# 브리핑·스프린트·일정 지연 관리 최종 기획안

작성: 2026-09-17 · 최종 검증: 2026-09-18 · 범위: 기획 및 화면 검토용 시안. 서비스 코드·Notion 데이터 변경 없음.

## 2026-09-18 추가 반영

최신 수정: 현재 스프린트는 목록에서 고르는 즉시 조회하며 별도 저장, 저장 이력, 순서 선택을 제거했다. 시안은 메인 스냅샷(data/dashboard.json)의 프로젝트·하위 업무·상위 작업 규칙 ID를 임베드해 같은 원천에서 계산한다. 메인의 진행 준비 필요는 현재 선택 범위의 시작 전 하위 업무에서 기한 초과를 제외한다. 원천 스냅샷은 2026-08-07이며 실시간 Notion 동기화가 아니므로 메인 반영 전 최신 스냅샷 재검증이 필요하다.

Notion 프로젝트의 현재 스프린트 속성을 스프린트별 업무 현황의 자동 기준으로 사용하지 않는다. 스프린트별 업무 현황은 사용자가 직접 선택하는 조회 필터이며, 최근 7일 언급량이나 현재 스프린트 값으로 자동 선택하지 않는다. 현재 시안은 실제 스냅샷에 존재하는 Sprint2·3·4·5·7·60·61만 목록화하고 Sprint60·스프린트60처럼 같은 값을 가리키는 표기는 하나로 합친다. 3.5·크리에이티브가 최신 스냅샷에 없다는 사실을 임의 데이터로 채우지 않는다.

스프린트 현황에는 기존 운영 분류인 **진행 중**, **기한 초과**, **가이드 위반**, **진행 준비 필요**를 다시 표시한다. 진행 중·완료·전체·시작 전은 실제 Sprint 집계에서 표시하고, 기한 초과와 가이드 위반은 스냅샷의 마감일·규칙 판정 원문으로 계산한다. 스프린트 미선택은 0건이 아니라 미계산으로 표시한다.

## 2. 조사에서 확인한 사실

### 실제 배포 화면

2026-09-17 [배포 화면](https://task-dashboard-eight-khaki.vercel.app)을 읽기 전용으로 확인했다.

- 화면은 AI 통합 브리핑 → 어제와 달라진 것 → 프로젝트 현황 → 스프린트별 업무 현황의 네 영역이다.
- 공용 현재 스프린트 기준은 모든 프로젝트에 적용된다. 텍스트 입력은 표기 오류와 선택지 불일치를 만들 수 있으므로 정규화된 스프린트 목록에서 선택하도록 한다. 비어 있는 상태에서 미계산 안내와 숫자 0이 함께 보여 의미가 충돌한다.
- 데이터 동기화는 9/17, 표시된 프로젝트 AI 분석은 9/11이다. ‘갱신 필요’ 상태로 과거 분석이 남아 있다.
- 프로젝트 두 개가 반폭으로 배치되고, 그 안에 다시 작은 카드가 나뉜다. 현재 진행 요약은 접힌 제목 부분과 본문에 반복된다.
- 실행 병목·확인 필요·다음 행동·분석 제한이 비슷한 색과 긴 문장으로 이어져 읽기 우선순위가 약하다.
- Git 부분 수집 상태도 존재한다. 스프린트 입력만 고쳐도 모든 분석 문제가 해결되는 상황은 아니다.

## 4. 회사 실행 우선순위

스프린트는 **이번에 진행하기로 한 범위**, 마감은 **시간상 긴급성**, 명시 우선순위와 의존관계는 **사업상 중요성·선행 필요성**으로 사용한다.

### 표시 규칙

1. `즉시 개입`: 명시적 긴급/0순위 업무, 직접 근거가 있는 출시·핵심 선행 병목, 당일 결정이 필요한 안건.
2. `마감 대응`: 미완료이며 기한 초과, 오늘 마감, 3일 이내 마감. 3일은 초기 제안값이며 날짜 기준은 KST 달력일이다.
3. `참조 범위 실행`: 최근 7일 Sprint 언급량이 높은 프로젝트별 후보의 미완료 업무. Notion 우선순위 → 마감 → 안정적 ID 순으로 정렬한다.
4. `확인 필요`: 마감/담당/참조 Sprint가 없어 판단을 제한하는 업무. 누락이라는 이유만으로 개발상 긴급 업무로 승격하지 않는다.

같은 업무는 가장 높은 해당 그룹에 한 번만 표시하되 여러 이유 배지를 유지한다. 마감 대응 안에서는 기한 초과 → 오늘 → 임박, 각 그룹 내 명시 우선순위 → 마감 오름차순으로 정렬한다. 명시 우선순위 미입력은 같은 시간 그룹의 입력값 뒤에 둔다. 오래 연체된 단순 업무가 전사 첫 화면을 독점하지 않게 상위 3건과 전체 목록 링크를 둔다.

중요도와 의존관계가 없는 데이터에서는 ‘시간 기준 우선 확인’이라고 설명한다. 의존관계는 상하위 관계만으로 추정하지 않는다. AI가 제시한 병목은 확인된 병목과 구분해 `확인 제안`으로 표시한다.

참조 후보 밖의 기한 초과/명시적 긴급 업무도 전사 AI 브리핑에서 누락하지 않는다. 스프린트 현황에서는 `선택 범위 밖 위험 N건`으로 보여주되 선택 범위의 숫자에는 섞지 않는다. 단순 조회 필터는 회사 AI 브리핑의 우선순위를 바꾸지 않는다.

각 안건의 통일 형식: **할 일 / 지금 봐야 하는 이유 / 담당 또는 확인할 역할 / 마감 / 출처·확인 시각**. 출처가 없으면 담당·날짜를 만들어 채우지 않는다.

### AI 출력 계약

- ‘공용 스프린트가 없으므로 회사 우선순위 판단 불가’는 금지한다.
- 프로젝트별 `currentScopes`, 원본 출처, 수집 기준 시각, 스프린트 밖 위험, 명시 우선순위를 입력한다.
- 프로젝트 범위 변경 시 범위 버전을 갱신한다. 같은 데이터·범위 버전으로 생성되지 않은 AI 결과는 `이전 기준 분석`이다.
- 최신 규칙 사실은 즉시 표시하고, 오래된 AI의 행동 권고는 접힌 `지난 분석`으로 이동한다. 과거 요약을 날짜만 바꿔 재사용하지 않는다.
- 프로젝트 한 곳이 미설정이어도 나머지의 계산을 막지 않는다. 해당 프로젝트는 스프린트 지표만 `미계산`, 마감·상태는 계산 가능 범위대로 제공한다.

## 5. 스프린트·크리에이티브 지원

### 운영 기준과 조회 필터 분리

- 원칙: **Notion의 현재 스프린트 필드는 스프린트 화면의 자동 기준으로 사용하지 않는다.** 스프린트별 업무 현황은 사용자가 직접 선택한 범위만 조회한다. 최근 7일 작업 행의 Sprint 언급량은 AI 통합 브리핑·프로젝트 요약에서 참고할 때만 사용한다.
- 대시보드에서 선택하는 스프린트는 조회용이다. 프로젝트를 바꾸거나 필터를 선택해도 Notion 원본·다른 사용자의 기준·AI 입력은 바뀌지 않는다.
- 최근 7일 조회는 기준일 포함 KST 7일로 고정하고, 후보별 언급 건수·조회 시각·프로젝트를 함께 저장한다. 데이터 수집 실패나 조회 제한은 0건이 아니라 `확인 불가`로 표시한다.
- 과거·현재 전체 스프린트는 검색 가능한 이력으로 남기고, 기본 선택은 비워 둔다. 사용자가 하나 이상 선택하면 해당 범위만 집계한다. 별도의 공용 현재 스프린트 원본은 만들지 않는다.

### 입력·표시·판정

- 스프린트 입력은 **Notion의 전체 Sprint 선택지를 보여주는 검색 가능한 다중선택 목록**으로 제공한다. 데이터 소스가 여러 개면 각 선택지와 작업의 원문 값을 합친 뒤 정규화한다. 화면을 열었을 때 자동으로 선택하지 않고, 사용자가 직접 하나 이상 고른 항목만 집계한다. 프로젝트를 바꿔도 사용자가 고른 스프린트 선택은 유지한다.
- 메인 브랜치의 기존 업무 탐색 기능을 유지한다. 선택한 프로젝트·스프린트 아래에 상위 업무와 작업항목을 계층으로 보여주고, 최신/과거 스프린트 순서를 바꾸며, 상위 업무와 관리 확인 상세를 펼쳐 본다. 새 브리핑에서는 이 동작을 네 가지 현황 카드 아래에 배치한다.
- `Sprint3.5`, `스프린트3.5`, `3.5스프린트`, `3.5`는 숫자형 3.5로 정규화하고 목록에는 **스프린트3.5 한 개만 표시**한다. `Sprint60`, `sprint60`, `스프린트60`도 **스프린트60 한 개**로 합친다. 공백·대소문자·선행 0 차이를 통합한다. 원문은 내부 별칭/근거 데이터에 보존하고, 어떤 별칭으로 검색해도 같은 항목을 찾는다. 전사 목록은 번호당 하나만 표시하되 실제 업무 집계에서는 프로젝트 ID를 유지한다.
- 0 및 정수·소수 번호를 지원한다. 소수는 버전 번호가 아니라 숫자이므로 3.50=3.5, 3.10=3.1로 정의한다. 모호한 문자열을 부분 숫자로 파싱하지 않는다.
- 숫자형 목록 정렬: 3 → 3.5 → 4 → … → 60 → 61. 숫자는 오름차순, 이름형은 별도 묶음으로 가나다순 표시한다. 현재값은 선택 상태로 구분하며 목록 순서는 바꾸지 않는다. 미지정 업무는 별도의 확인 필터에서 처리한다.
- `크리에이티브`, `Alpha`, `CPI 개발리스트`는 이름형 작업 묶음으로 보존한다. 번호와 과거/미래를 비교하지 않는다. 이름형은 명시적으로 현재에 지정됐을 때만 `현재`다.
- 숫자형과 이름형이 함께 현재여도 숫자형끼리의 과거/미래 판정을 유지한다. 현재 숫자가 여러 개면 정확 일치만 현재, 최솟값보다 작으면 과거, 최댓값보다 크면 미래, 그 사이 미선택 값은 `선택 외`다.
- 완료 작업만 있는 이름형도 선택지에 남긴다. 예: 크리에이티브 선택 시 현재 진행 0건과 완료 내역 보기, 미설정/오류와 구별한다.
- 프로젝트가 다르면 동일한 3.5도 별개 범위다. 전사 조회는 프로젝트별 범위를 합집합으로 모으고 업무 ID로 중복 제거한다.
- 기본 집계 단위는 하위 작업항목. 자식의 실제 Sprint가 있으면 그것을 사용하고, 없을 때만 부모 값을 상속하며 상속 표시를 남긴다. 부모와 자식 값이 다르면 자식값을 우선하고 부모는 맥락으로 연결한다. 상위 단독 작업/관리 항목은 별도 집계해 분모를 혼합하지 않는다.
- 완료율은 선택 범위의 완료 하위 작업 / 중단·취소를 제외한 전체 하위 작업. 완료 상위의 자식도 데이터에는 남겨 분모를 일관되게 한다. 대상 0개는 0%가 아니라 `대상 없음`이다.

## 6. 일정 지연 기록과 평가 조회

사용자 표현의 두 해석을 모두 지원한다. **조회 시작일**과 **업무별 약속 마감**은 서로 다른 값이다. 기본 조회 기간은 사용자가 선택한 시작일부터 종료일까지이며, 아직 실제 시작일은 정하지 않았다.

| 지표 | 정의 | 예 |
|---|---|---|
| 일정 연장 횟수 | 미완료 업무의 확정 마감을 더 늦은 날짜로 바꾼 유효 사건 수 | 9/20→9/22→9/25이면 2회 |
| 마감 초과 업무 수 | 고정 기준 마감까지 완료되지 못한 고유 업무 수 | 같은 업무가 5일 연체돼도 1건 |
| 지연일 | 기준 마감부터 실제 완료 또는 조회 기준일까지의 달력일 | 9/20 마감, 9/23 완료면 3일 |
| 평가 검토 결과 | 기록을 평가에 포함·제외·확인 중으로 분류 | 외부 대기/범위 변경/오입력 정정 등의 근거 확인 |

### 기준 마감

- 도입 시점 이후 최초로 합의한 유효 마감을 기준으로 고정한다. 일정이 바뀌어도 원래 기준을 덮어쓰지 않는다.
- 도입 이전 업무는 관측 시작 당시 마감을 `도입 시점 기준`으로 저장한다. 최초 약속일이라고 표현하지 않는다.
- 기획 범위의 실질적 변경은 새 작업을 만드는 기존 가이드를 우선한다. 불가피한 기준 재설정은 승인된 별도 기록으로 남겨 원래 기준·변경 기준을 모두 확인하게 한다.
- 평가 시작일을 바꿔도 원장·기준 마감은 초기화되지 않는다.

### 사건·기간 규칙

- 마감 연장 1회는 한 번의 유효한 변경 사건이다. 동일 사건 재수집/재시도는 0회 추가, 같은 날 실제 두 번 연장은 2회다.
- 미입력→첫 마감 지정, 마감 앞당김, 시작일만 변경, 마감 삭제는 연장 횟수에 넣지 않는다. 삭제·정정도 별도 사건으로 기록한다.
- 마감 삭제·뒤로 미루기·완료 처리로 이미 생긴 지연 기록을 지우지 않는다. 완료 이후 단순 날짜 정정은 일정 연장에 포함하지 않는다.
- 동일 작업 재개는 기존 지연 건수를 중복 생성하지 않는다. 완료 후 추가 작업은 새 작업 ID로 만드는 기존 가이드를 따른다.
- 날짜만 있는 마감은 KST 해당 날짜 종료까지 유효, 다음날 00:00부터 초과다. 시각이 있는 마감은 해당 시각과 시간대를 존중한다.
- 기간은 KST 시작일 00:00 이상, 종료일 다음날 00:00 미만. 일정 연장은 사건 발생 시각으로, 마감 초과 업무는 최초 초과 시점으로 집계한다.
- 시작일 전에 이미 초과한 업무는 `이월 지연`으로 따로 표시하고 기간 내 신규 지연 수에 섞지 않는다. 신규 지연의 지연일은 기간 종료 또는 완료 시점에서 계산한다. 이월 지연일은 별도 표기한다.
- 정확한 발생 시각/완료 시각을 모르면 `관측 시각`과 실제 발생 가능 구간을 기록한다. 평가 기간 경계에 걸리면 자동 확정하지 않는다. last_edited_time을 완료 시각으로 사용하지 않는다.
- 담당자 변경 후에도 사건 당시 담당자 ID를 보존한다. 공동 담당은 공동 항목으로 표시하고 회사 합계는 업무 ID 기준으로 한 번 센다. 화면에서 개인별 건수를 단순 합산하지 않는다.

### 저장 및 기록 경로

평가용 이력은 활성 대시보드와 분리된 **영구 일정 변경 원장**으로 관리한다. 기존 Notion 운영을 활용하는 일정 변경 기록 DB를 우선안으로 한다. 이번 단계에서는 생성하지 않는다.

필수 사건 필드: 사건 ID, 업무 ID/링크, 프로젝트 ID, 이전·새 마감, 기준 마감 버전, 발생 시각/관측 시각/정확도, 당시 상태·담당자 ID, 사유 분류·설명, 관련 근거, 확인자·확인 상태, 평가 포함/제외 및 이유, 수집 실행 ID. 변경 이력의 정정은 삭제 대신 정정 사건으로 남긴다.

1. 확정 일정 변경은 기존 ‘이전 날짜→변경 날짜+사유’ 공유 절차를 구조화한 기록으로 남긴다. 해당 원장과 실제 업무 마감의 일치 여부를 검증한다.
2. 직접 Notion 마감만 고친 경우 자동 수집은 전후 상태 차이를 `관측된 변경`으로 남긴다. 원장 누락 확인 대상으로 표시한다.
3. 일별 스냅샷이나 webhook만으로 모든 실제 변경 횟수를 보장하지 않는다. 정확한 횟수가 필요하면 모든 확정 변경을 기록하는 운영 절차가 필수다. 기록 경로 밖의 중간 변경은 ‘알 수 없음’이다.
4. 동기화는 안정적 사건 ID로 멱등 처리하고 직전 원장과 대조한다. Notion에는 DB 수준 유일성 제약이 없으므로 쓰기 직렬화, 재시도 대조, 중복 복구 검사를 구현 조건으로 둔다. 처리량이 이를 넘어서는 경우에만 별도 저장소를 검토한다.
5. 원본 데이터 수집 직후, 완료·정지·중단 화면 필터 적용 전에 관측 및 상태 이력을 보존한다. 삭제/권한 상실/수집 실패는 완료나 정상으로 간주하지 않는다.
6. 기존 저장본으로 복구한 과거 기록은 `부분 관측`으로 분리한다. 자료 없는 과거를 0회로 표시하지 않는다. 수집 완전성 표시와 실제 사용 가능 시작일을 항상 제공한다.

### 평가 화면

브리핑에 네 번째 영역을 만들지 않는다. `스프린트별 업무 현황`에는 선택 범위의 일정 위험 요약과 이력 링크를 두고, 누적 평가는 기존 `담당자` 화면의 `일정 이력`으로 제공한다.

조회: 시작일·종료일·프로젝트·담당자·사유·확인 상태. 주 표시: 기간 내 신규 마감 초과 업무 수, 일정 연장 횟수, 지연일, 이월 지연, 미확인 기록. 완료 업무도 이력에 남긴다.

**사건 집계와 지연율의 분모는 분리한다.** 기간 내 신규 지연 건수는 최초 초과 시점 기준이다. 별도의 마감 준수율을 표시할 때는 해당 기간에 기준 마감이 속한 동일 업무 집합을 분자·분모 모두에 사용한다. 예를 들어 9/20 마감이 9/21 처음 초과하면 9/21 신규 지연 사건이지만, 마감 준수율에서는 9/20 마감 대상에 속한다. 두 집계를 나누어 보여주고 서로 나누지 않는다.

마감 준수율의 대상은 유효한 기준 마감과 충분한 완료 관측이 있고 조회 기준 시각에 판정 가능한 업무다. 기간 종료가 오늘인 경우 오늘 끝까지 유효한 미완료 업무는 `아직 판정 전`으로 분리한다. 기한 미입력·관측 불충분·취소·판정 전 수를 각각 표시하고, 완료 업무는 대상에서 빠지지 않는다. 마감 이전 확정 취소는 평가 대상에서 제외할 수 있으나, 이미 지연된 뒤 취소/중단했다고 원래 지연 사실을 소급 삭제하지 않는다. 평가 제외는 사유와 확인자를 남기는 별도 결정이다.

평가에는 단순 횟수 순위나 자동 점수 차감을 만들지 않는다. 업무량·지연 사유·합의된 범위 변경·외부 의존과 함께 사람이 검토한다. 평가 제외는 운영상 발생한 연장 사건을 지우지 않는다. 개인별 평가용 이력은 관리자 접근 범위에서만 제공하며, 현재 배포의 일반 공개 대시보드에 그대로 노출하지 않는다.

### 세 영역의 역할

| 영역 | 답할 질문 | 본문 형식 |
|---|---|---|
| 1. AI 통합 브리핑 | 회사에서 지금 무엇을 먼저 확인할까? | 한 줄 요약 + 우선 안건 최대3개, 이유·담당·마감·근거. 추가 안건 펼치기 |
| 2. 프로젝트 현황 | 이 프로젝트는 어디까지 왔고 무엇이 막혔나? | 프로젝트 선택 + 현재 진행 요약 + 전체 폭의 항목별 행 |
| 3. 스프린트별 업무 현황 | 선택 범위에서 누가 무엇을 진행하나? | 프로젝트별 현재 범위 + 조회 필터 + 지표 + 작업 표 |

세 영역의 외곽 패딩·제목 크기·메타정보 위치·본문 행·상세 펼치기를 통일한다. 기존 ‘어제와 달라진 것’은 1번의 변경 요약 및 3번 업무 이력으로 옮긴다. 판단 근거에 필요한 데이터 신뢰 정보는 삭제하지 않는다.

### 프로젝트 선택

- 가로 프로젝트 선택 막대에서 프로젝트를 고르면 해당 프로젝트 내용이 **화면 전체 폭**에 나타난다. 피자레디 / 포지앤포춘 / …가 탭처럼 동작한다.
- 보기 방식 토글과 가로 비교 화면은 제공하지 않는다. 프로젝트 선택만으로 내용이 바뀌는 단일 화면으로 구성한다.
- 프로젝트 수가 늘어나면 선택 막대만 가로 스크롤하고 ‘전체 프로젝트 검색’을 제공한다. 본문 전체의 가로 스크롤은 기본 읽기 모드에서 금지한다.
- 데스크톱과 모바일 모두 선택한 프로젝트의 본문만 표시하며, 프로젝트별 정보 카드를 나란히 늘어놓지 않는다.
- 프로젝트 선택은 2번 영역에만 적용한다. 3번 프로젝트 필터는 독립적이다. `이 프로젝트 업무 보기`를 눌렀을 때만 3번 필터를 명시적으로 연결한다. 전사 브리핑은 그대로 유지한다.
- 정렬은 프로젝트 이름 또는 사용자가 저장한 순서로 안정적으로 유지한다. 갱신할 때마다 위험도에 따라 탭을 재배치하지 않는다. 신규 프로젝트 자동 추가, 선택 프로젝트 삭제 시 첫 유효 프로젝트로 전환하고 안내한다.
- 탭은 선택 상태·키보드 좌우 이동·Home/End·포커스 표시를 지원한다.

### 일곱 종류 정보를 네 묶음으로 정리

화면 순서: 프로젝트 헤더 → **현재 진행 요약** → 다음 행동 → 진행 근거(납품·검증/성과·실험) → 막힌 일·확인할 일 → 근거와 제한. 회사 AI 브리핑은 전사 개입 안건, 프로젝트 다음 행동은 해당 프로젝트 실행이므로 같은 장문을 복제하지 않는다.

디자인 원칙: 밝은 중립 본문, 구분선과 타이포로 계층을 만든다. 분홍 배경·그라데이션·카드 안 카드의 반복을 줄이고, 강조색은 선택/행동에만 쓴다. 빨강은 확인된 초과/장애, 주황은 확인 필요, 회색은 참고. 색 없이도 상태 라벨을 읽을 수 있어야 한다. 본문 14~16px, 줄간격 1.6 전후, 60~85자 내외 읽기 폭을 목표로 한다. 실제 대비와 읽기 시간은 구현 후 확인한다.

정보가 없을 때: `확인된 근거 없음`, 분석을 못했을 때: `분석 미실행`, 수집 실패일 때: `확인 불가`, 실제 완료 후 진행 업무가 없을 때: `진행 0건`을 구별한다. 제한을 모두 접어 중요한 불확실성이 사라지게 하지 않는다.

## 10. 검증·잔여 사항

기획 검증에서 전사 공용 스프린트 강제, 소수 정렬, 이름형 현재 자동 추정, 완료 업무 누락, 일별 횟수 중복, 오래된 AI 재사용, 과거 기록 과신을 찾아 위 정책에 반영했다.

- 확인 완료: 배포 화면과 상세 레이아웃, 실제 Notion 현재값/선택지/행 집계, 로컬 스프린트 오류 재현, 일별 이력 한계.
- 제안 기본값: 일정 연장과 마감 초과를 모두 기록, 마감 임박3일, KST 달력일, 프로젝트 선택 방식. 사용자 답변이 오면 지연 주 지표를 조정하되 원시 이력은 유지한다.
- 구현 전 선행조건: 배포 기준 소스 확보·정합성 확인. 이번 문서는 서비스 코드 변경을 시작하는 승인이 아니다.
- 실제 평가 시작일·기준 마감 합의 방식·원장 변경기록 책임은 설정 시 지정한다. 누락 시 임의로 오늘부터 평가했다고 표시하지 않는다.
- 남은 검증: 실제 사용자 읽기 시간, 프로덕션 데이터 규모에서 원장 일치율, 관리자 접근 체계. 정적 시안은 정보 구조 검토용이며 이 기능들이 구현된 서비스가 아니다.
