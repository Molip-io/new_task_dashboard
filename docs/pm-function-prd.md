# MOLIP PM 기능 PRD

버전 2.0 · 2026-09-30 · PM Control Tower PRD v1.2를 대체한다.

이 문서는 "PM 역할을 하는 에이전트"가 아니라 **회사에서 PM 기능이 실제로 수행되게 하는 체계**를 정의한다. 체계는 사람(역할), 기록(스프린트 일정), 에이전트 세 부분으로 이루어진다. 에이전트는 그중 하나다.

## 1. 문제

대표는 프로젝트가 어떻게 진행되는지, 어디가 막혔는지 알고 싶다. 병목은 **기준선과 비교할 때만** 보인다. 기준선은 스프린트의 기간(킥오프일 → 목표 업로드일)과 약속한 스펙이다. 지금은 이 기준선을 정하고, 바뀌면 고치는 책임자가 없다.

근거 (2026-09-29~30, Notion 원본 확인):

| 관찰 | 의미 |
|---|---|
| SP3 목표일은 프로젝트 리스트·작업 DB·로드맵·회의록에서 찾지 못했고 Slack "9/3 빌드 전달일"에만 있었다. SP4 목표일 10/15도 일정 행이 생기기 전까지 Slack(9/28)에만 있었다 | 목표일에 주인이 없었고, 같은 일이 반복됐다 |
| SP3 로드맵의 완료 기준은 "도크에서 구매"인데 실제 빌드는 "작업대 해금"이었고 문서는 갱신되지 않았다 | 한 번 쓰고 방치되는 문서는 기준선이 될 수 없다 |
| SP3 스펙 20개는 완료 19 + 중단 1로 정리됐지만, 세부 작업 57건은 빌드가 나간 뒤에도 열려 있었다 | 스펙 단위는 관리되고, 세부 작업 단위는 갱신이 빠진다 |
| 빌드 3.5.0(Sprint3)은 빌드노트에 버전·업로드일(9/4)로 정확히 남았다 | 외부로 나가는, 쓰는 곳이 있는 기록만 유지된다 |
| "현재 스프린트" 설정이 빈 채 전달된 날, 에이전트가 스프린트를 추론하도록 바뀌었다 | 기준선이 없으면 추론이 그 자리를 대신한다 |

지금 시스템이 자동화한 것은 PM의 **감시** 쪽이다. 빠진 것은 **기준선을 정하고 고치는** 쪽이다.

## 2. 목표와 성공 기준

### 목표

1. 진행 중인 스프린트마다 **스프린트 일정 행**(§5)이 있고, 기간과 범위가 최신이다.
2. 대표가 Slack을 뒤지지 않고 세 질문에 답할 수 있다.
   - 이번 빌드가 목표일 대비 며칠 늦었나, 또는 여유가 있나?
   - 무엇이 끼어들었고, 그 때문에 무엇이 밀렸나?
   - 지금 누가 무엇을 기다리고 있나(대표 본인 포함)?

### 성공 판정 (파일럿 종료 시)

| ID | 기준 | 측정 |
|---|---|---|
| S1 | 다음 빌드 3개에서 대표가 세 질문에 Slack 없이 답한다 | 빌드마다 대표가 직접 확인해 기록 |
| S2 | 스프린트 일정 행이 킥오프 후 **2영업일 안에** 생긴다 | 행 생성일 − 킥오프일 |
| S3 | 목표일·범위를 바꾼 결정이 **다음 영업일까지** 일정 행 날짜와 Sprint 태그에 반영된다 | 회의록·Slack의 변경 결정 수 대비 반영 수 |
| S4 | 빌드 업로드 후 **2영업일 안에** 약속 스펙이 모두 완료 또는 다음 스프린트로 이월되고, 퍼블리셔 결정 후 **다음 영업일까지** 일정이 종료된다 | 업로드일·결정일 대비 단계 전환일 |
| S5 | PD가 일정 관리에 쓰는 시간이 스프린트당 **2시간 이하**다 | PD 자가 기록 |

S2~S4가 "PM 기능이 수행되고 있는가"를 잰다. 이 지표가 무너지면 화면 품질과 무관하게 실패다.

## 3. 범위

- **일정 관리 대상:** 포지 앤 포춘, 피자레디. 목록은 `config.json`의 `validation.sprintScheduleProjects` 한 곳에서 관리한다. 대상 프로젝트에 열린 일정 행이 없으면 "스프린트 일정 없음" 경고를 띄운다.
- **파일럿 측정:** 포지 앤 포춘 스프린트4(목표 업로드 10/15)부터 빌드 3개.
- **라이브작(피자레디):** 빌드는 월 1회가 목표지만 핫픽스로 자주 밀리고, 여러 스프린트가 겹친다(9/30 기준 Sprint61과 Sprint62 일부가 함께 진행 중). 여기서는 스프린트 일정과 함께 **비정기 빌드**(퍼블리셔 요청 재빌드·핫픽스) 기록이 핵심이다.
- **그 외 프로젝트:** 지금 브리핑 그대로다.
- **비목표:** §9.

## 4. 구성

| 구성 요소 | 무엇 | 없으면 |
|---|---|---|
| **역할** | 기준선을 정하고 고치는 책임자. PD | 기록이 낡고, 에이전트가 추측으로 채운다 |
| **기록** | 스프린트마다 일정 행 1개. 범위는 Sprint 태그로 자동으로 정해진다 | 비교 기준이 없어 병목을 잴 수 없다 |
| **에이전트** | 기록을 읽어 대조·측정·브리핑하고, 갱신이 빠진 곳을 찾는다 | 기록 부담이 커지고 변경을 놓친다 |

### 4.1 역할

| 역할 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| **PD** (PD가 없으면 대표) | 목표 업로드일을 정해 슈퍼센트에 통보하고, 바뀌면 일정 행의 끝 날짜를 고치고, 결과가 나오면 일정을 완료로 바꾼다. 일정 행 자체는 대표를 포함해 누가 만들어도 된다. 날짜가 제때 정해지고 고쳐지는 것이 기준이다 | 작업 상태를 하나하나 갱신하는 일 |
| **팀장·작업자** | 작업 상태를 갱신하고, 이월·재배치할 때 스펙의 Sprint 태그를 바꾼다(지금 습관) | 목표일 결정 |
| **대표** | 날짜·태그에 반영되지 않은 변경은 결정으로 보지 않는다는 원칙을 지키게 한다. 대표 본인의 범위 결정도 같다 | PM 역할 대행 |
| **에이전트** | §6 | 일정 값 확정, Notion 수정 |

### 4.2 스프린트 흐름과 사람이 하는 일

| 시점 | 사람이 하는 일 | 일정 단계 | 에이전트가 하는 일 |
|---|---|---|---|
| 기획 확정 전 | 누구든 일정 행을 `시작 전`으로 만든다(선택) | 선행 | 선행 작업으로만 표시, 지연 판단 없음 |
| 작업자 킥오프 | 기간(킥오프일 → 목표 업로드일)을 넣고 `진행 중`으로 바꾼다. 목표일은 PD가 정해 슈퍼센트에 통보하고, 이견이 있으면 합의한다 | 개발 중 | 목표일 대비 진행, 끼어든 작업, 기다리는 작업을 본다 |
| 범위·일정 변경 | PD는 끝 날짜만, 팀은 스펙의 Sprint 태그만 고친다 | 개발 중 | 변경을 자동 기록하고 이유를 회의록·Slack에서 찾아 붙인다 |
| 약속 스펙 완료 | 약속 스펙을 완료하거나 다음 스프린트로 이월한다. 이후 내부 QA(일감 없음), 빌드 업로드, 퍼블리셔 테스트가 이어진다 | **테스트 중**(자동) | 슈퍼센트 미팅·공유 채널·팀 분석에서 QA·업로드·테스트 결과를 모은다 |
| 퍼블리셔 결과와 다음 결정 | PD가 `완료`로 바꾼다. 핫픽스면 새 스프린트(예: 스프린트3.5)로 일감과 일정 행을 만든다 | 종료 | 결과를 일정에 붙여 보여 준다 |

## 5. 스프린트 일정

### 5.1 일정 행 형식

일정은 **작업 현황 DB에 스프린트마다 행 하나**로 둔다. 새 속성은 없고 기존 속성의 의미만 정한다.

| 내용 | 담는 곳 | 규칙 |
|---|---|---|
| 식별 | `작업` = **`Sprint` 태그 값 + " 일정"** (예: "스프린트4 일정", "Sprint61 일정") | 제목이 정확히 이 형식이고 상위 항목이 없는 행만 일정으로 읽는다. 상위·하위 항목은 비워 둔다 |
| 프로젝트·스프린트 | `프로젝트`, `Sprint` | |
| 책임자 | `담당자` = PD(없으면 대표) | |
| **기간** | `시작날짜 <-> Dead Line` = 작업자 킥오프일 → 목표 업로드일 | 항상 기간으로 넣는다. 시작일은 킥오프일로 고정하고 스펙들의 날짜로 계산하지 않는다. 예전에 작업하다 옮겨 온 스펙이 있어도 기간은 늘어나지 않고, 킥오프 전 작업은 선행 작업으로 본다. 단일 날짜는 쓰지 않는다(기존 규칙이 '마감일 없음'으로 읽는다) |
| **약속 범위** | 같은 프로젝트·Sprint 태그를 가진 **스펙(최상위 작업)** 중 `중단`이 아닌 것 | 따로 연결하지 않는다. 세부 작업은 범위 계산에 쓰지 않는다 |
| 단계 | `Status` | §5.2 |
| 이 빌드로 확인할 것 | 페이지 본문 | 선택. 퍼블리셔 테스트 결과를 해석할 때 쓴다 |

완료 기준 문서는 두지 않는다. 약속한 스펙이 모두 완료되면 개발이 끝난 것이다. 설계가 바뀌었는데 기록이 안 되는 문제는 에이전트의 변경 감지(F2)로 잡는다.

### 5.2 단계

| 단계 | 조건 | 판단 |
|---|---|---|
| 선행 | `Status` = 시작 전 | 목표일·지연 판단 없음. 스펙은 후보 범위로만 표시 |
| 개발 중 | `Status`가 열려 있고 약속 스펙 중 미완료가 있음 | 목표일 대비 진행 판단 |
| 테스트 중 | `Status`가 열려 있고 약속 스펙이 모두 완료됨 | 개발 완료 상태다. 이후 내부 QA, 빌드 업로드, 퍼블리셔 테스트가 이어진다. PD가 상태를 바꾸지 않아도 자동으로 판정한다. QA는 일감으로 잡지 않고 상태 갱신이 늦을 때도 있어서, 스펙 완료와 실제 업로드는 며칠 어긋난다(포지 SP2는 업로드보다 약 6일 먼저, SP3는 약 5일 늦게 모두 완료). 빌드노트 업로드일을 읽을 수 있으면 QA 중과 퍼블리셔 테스트 중으로 나눈다(§12) |
| 종료 | `Status` = 완료 | 결과까지 닫힘 |
| 취소 | `Status` = 중단 | |

### 5.3 현재 스프린트

- **현재 스프린트는 하나가 아니다.** 개발 중·테스트 중인 일정이 모두 현재다. 예: 포지는 SP3 빌드 뒤 핫픽스 SP3.5와 SP4가 함께 진행됐다. 피자레디는 Sprint60 스펙이 모두 완료된 뒤(9/9 업로드) Sprint61이 개발 중이고, Sprint62 일부가 먼저 진행 중이다.
- 대표가 따로 지정하는 설정값은 없다.
- 개발 중·테스트 중 일정이 없으면 에이전트가 최근 7일의 Notion·Slack·회의록·Git 근거로 현재 스프린트를 판단한다. 이때는 목표일 대비 지연처럼 기준선이 필요한 판단을 하지 않는다.
- 일정이 있어도 에이전트는 최근 7일 활동과 대조한다. 일정 밖 스프린트의 작업이 실제로 진행 중이면 "스프린트 일정 없는 진행 작업", 개발 중 일정인데 7일간 활동이 없으면 "7일간 활동 없는 일정"으로 표시한다.

### 5.4 변경 기록

**사람은 기준선만 최신으로 둔다. 결정 내용은 적지 않는다.**

| 무엇 | 누가 | 어떻게 |
|---|---|---|
| 목표일이 바뀜 | PD | 일정 행의 끝 날짜만 고친다 |
| 범위가 바뀜(추가·이월·재배치) | 팀장·작업자 | 스펙의 Sprint 태그만 바꾼다. 예: SP61에서 미리 한 스펙을 SP60으로, 완성했지만 출시를 미룬 스펙을 다음 스프린트로 |
| 무엇이 언제 바뀌었나 | 에이전트 | 매일 스냅샷 비교로 자동 기록 |
| 왜 바뀌었나 | 에이전트 | 변경일 근처의 회의록·Slack을 찾아 연결. 못 찾으면 "이유 미확인" |
| 예외 | PD | 이유가 회의록·Slack 어디에도 없을 때(구두 결정 등)만 일정 행에 댓글 |

회의록·Slack에 새 목표일이나 범위 변경이 나왔는데 날짜·태그가 그대로면 에이전트가 "기준선 미갱신"으로 표시한다.

### 5.5 일정 행 틀

작업 현황 DB의 템플릿으로 등록해 스프린트마다 기본 일감으로 만든다.

- 속성: `프로젝트`, `Sprint`, `담당자` = PD, `시작날짜 <-> Dead Line` = 킥오프일 → 목표 업로드일, `Status`
- 본문(선택):

```
## 이 빌드로 확인할 것
- (퍼블리셔 지표로 무엇을 보려는지 1~2문장)
```

## 6. 에이전트

기존 시스템(수집·규칙·스냅샷·브리핑)을 그대로 쓰고 역할을 바꾼다. 대표용 요약기에서 **일정 대비 비교기 + 갱신 누락 탐지기**로.

### 6.1 기능

| 기능 | 입력 | 출력 | 받는 사람 |
|---|---|---|---|
| F1. 일정 읽기 | 일정 행, 스펙 상태 | 단계, 현재 스프린트, 목표일 대비 진행 | 대표 브리핑 |
| F2. 변경 감지 | 스냅샷 비교, 회의록, Slack | 기간·범위 변경과 그 이유, "기준선 미갱신" | 대표 브리핑, PD |
| F3. 결과 수집 | 슈퍼센트 미팅 회의록, 공유 채널, 팀 분석 | 테스트 중 일정의 결과·후속 결정 | 대표 브리핑, PD |
| F4. 병목 측정 | 매일 스냅샷 | §7 지표 | 대표 |
| F5. 대표 브리핑 | 일정 + §7 지표 | 프로젝트별 세 질문(§2)의 답 | 대표 |
| F6. 지연 근거 읽기 | 작업 페이지 댓글 | 지연 사유·변경 날짜·PD 태그 판정 | 팀장 |
| F7. 갱신 누락 찾기 | 작업 상태, Sprint 태그, Git·Slack 활동 | 갱신이 필요한 작업(담당자별) | PD, 팀장 |

### 6.2 F7 갱신 누락

에이전트를 만드는 목적 중 하나다. Notion을 최신으로 두지 않는 팀원이 갱신하게 한다. 에이전트는 직접 고치지 않는다.

| 조건 | 예 (9/30 확인) |
|---|---|
| 스펙이 완료·중단됐는데 세부 작업이 열려 있음 | SP3: 중단된 스펙 아래 세부 작업 33건 |
| 세부 작업의 Sprint 태그가 스펙과 다름 | SP3: 상위가 다른 스프린트인 세부 작업 12건 |
| Git·Slack에 작업 흔적이 있는데 Notion은 시작 전 | |
| 기한 초과인데 지연 댓글 없음 | 기존 지연 규칙 |
| 테스트 중 일정에 남은 미완료 세부 작업 | |

지금은 첫 두 조건을 확인필요 화면에 담당자별로 표시하는 것까지 한다(나머지 조건은 기존 규칙이 잡는다). 담당자가 없는 작업은 PD가 받는다. **담당자에게 Slack 알림을 보내는 것은 설계만 두고 보류한다.** 착수하면 담당자별로 하루 1회 묶어 보내고(PD 참조), 작업 링크와 바꿀 내용을 함께 적고, 채널 전체 공지는 하지 않는다. 범위는 개발 중·테스트 중 일정의 작업이고, 효과는 알림 후 3영업일 안 갱신률로 잰다. 그때 Slack 토큰에 메시지 보내기 권한을 추가한다(대표가 Slack 앱 설정에서 부여).

### 6.3 하지 않는 일

- 추론값을 일정 값으로 쓰거나 Notion 작업 상태·태그를 바꾸기.
- 일정이 없을 때 기준선이 필요한 판단(목표일 대비 지연, 이월률) 하기.
- 담당 배정, 개인 평가용 기록.

## 7. 병목의 정의

병목은 **기다림, 끼어듦, 뒤집힘**으로 잰다. 모두 매일 쌓는 스냅샷으로 계산한다. 대표 본인도 병목 후보에서 빼지 않는다.

| 종류 | 지표 | 계산 |
|---|---|---|
| 기다림 | '확인 요청' 체류일 | Notion은 상태 변경 시각을 주지 않으므로, 매일 스냅샷에 상태를 처음 관찰한 날을 이어서 기록하고 그날부터 센다. 관찰 시작 전 기간은 빠지므로 실제 대기는 같거나 더 길다 |
| | 대표 결정 대기일(추정) | 에이전트가 회의록 "대표 결정 필요"에 처음 나온 회의일부터, 이후 "결정된 사항"에 나오지 않은 동안을 센다 |
| | QA 기간 | 빌드노트 QA 기간. 빌드노트 DB 연결이 필요하다(§12) |
| 끼어듦 | 비정기 빌드 비율 | 비정기 빌드 수 / 전체 빌드 수. 빌드노트 DB 연결이 필요하다(§12) |
| | 밀린 약속 스펙 수 | 핫픽스 기간에 다른 스프린트로 태그가 바뀐 스펙 수 |
| 뒤집힘 | 목표일 변경 횟수 | 일정이 열린 뒤 끝 날짜가 바뀐 횟수. 매일 스냅샷 비교 결과를 일정별로 누적한다 |
| | 재배치 횟수 | 개발 중·테스트 중 일정으로 들어오거나 나간 스펙 수(Sprint 태그 변경), 일정별 누적. 선행 일정 안의 이동은 세지 않는다 |
| | 이월률 | 빌드 업로드 시 미완성으로 다음 스프린트로 옮긴 스펙 / 약속 스펙. 완성했지만 출시를 미룬 스펙은 지연이 아니므로 따로 센다 |

## 9. 비목표

- 에이전트가 일정 값이나 작업 상태를 자동으로 기록하기.
- 담당 배정, 채널 전체 공지, 하루 1회를 넘는 개인 알림.
- 게임 지표의 자동 성과 판정.
- 개인 생산성 평가.

## 10. 단계

| 단계 | 내용 | 상태 · 다음 단계 조건 |
|---|---|---|
| **0. 수동 일정** | 스프린트마다 일정 행을 만들고 날짜를 유지한다. 대상 프로젝트에 열린 일정이 없으면 경고한다 | 진행 중. 포지 "스프린트4 일정"(9/7 → 10/15)이 있다. 경고는 구현을 마치고 main 머지를 기다린다. 통과 조건: 피자레디 일정 행이 생기고, 목표일이 바뀌면 다음 영업일까지 끝 날짜가 고쳐진다 |
| **1. 일정 읽기** | ① 일정 행을 수집 직후 작업 목록에서 분리해 스펙 요약·완료율·관리 누락 규칙에서 뺀다 ② 단계를 자동 판정한다(§5.2) ③ 에이전트 입력에 `projects[].sprintSchedules`를 넣는다 ④ 개발 중·테스트 중 일정이 있으면 그 스프린트가 브리핑 기준이고(`basis=schedule`), 결과 검증이 이를 강제한다. 없으면 7일 추론(`basis=recent-activity`) ⑤ 화면에 "스프린트 일정 기준"을 표시한다 | 구현을 마치고 main 머지를 기다린다. 단계 0을 통과해야 의미가 있다 |
| **2a. 기준선 비교** | 일정별 목표일 대비 진행(남은 날, 기간 경과율, 약속 스펙 완료율, 지연 일수)을 계산한다. 스냅샷 비교로 스펙 재배치(Sprint 태그 변경)·목표일 변경·단계 전환을 기록한다. 에이전트는 변경 이유를 회의록·Slack에서 찾아 붙이고(F2), 기준선 미갱신을 표시하고, 테스트 중 일정의 결과를 모은다(F3) | 구현을 마치고 main 머지를 기다린다. 9/30 기준 포지 SP4: 목표까지 15일, 기간 61% 경과, 약속 스펙 완료 19% |
| **2b. 갱신 누락** | F7 판정 두 가지를 확인필요 화면에 담당자별로 보여 준다: 완료·중단된 스펙 아래 열린 작업, 스펙과 Sprint 태그가 다른 작업. 일정 관리 대상 프로젝트에만 적용한다 | 구현을 마치고 main 머지를 기다린다. 9/30 기준 포지 56건(열린 작업 21, 태그 불일치 35), 이 중 41건은 담당자가 없다. 피자레디 0건 |
| **2c. 병목 지표** | 확인 요청 체류일, 목표일 변경·재배치 횟수를 매일 스냅샷에 누적하고 에이전트 입력으로 넘긴다. 대표 결정 대기일은 에이전트가 회의록에서 센다 | 구현을 마치고 main 머지를 기다린다. 이력은 첫 수집일부터 쌓인다 |
| 2d. 남은 지표·화면 | QA 기간, 비정기 빌드 비율, 이월률. 대표 화면의 작업 단위 경고를 PD·팀장 보기로 이동 | 빌드노트 DB 연결과 화면 결정(§12)이 먼저다 |
| 3. 갱신 알림 | F7 Slack 알림 착수 | 갱신 누락이 표시만으로 줄지 않을 때 |
| 4. 운영 판단 | 빌드 3개 후 PD가 계속 맡을지, PM을 채용할지 정한다. 채용하면 §4.2의 흐름이 직무기술서다 | — |

단계 0이 가장 싸고 중요한 시험이다. 사람이 일정의 날짜를 제때 정하고 고치지 못하면 에이전트를 붙여도 기준선이 유지되지 않는다. 행을 누가 만드는지는 상관없다.

## 11. 반드시 참이어야 하는 전제

| 전제 | 틀리면 | 확인 방법 |
|---|---|---|
| 목표 업로드일이 킥오프 때 정해지고, 바뀌면 다음 영업일까지 일정 행에 반영된다. 날짜는 PD(없으면 대표)가 정하고 행은 누구든 고칠 수 있다. 이 문서 전체가 기대는 전제다 | 기준선이 낡아 진행·지연 판단이 틀린다 | 단계 0 통과 조건으로 확인 |
| 퍼블리셔 요청이 슈퍼센트 공유 채널(`s2_*`, 이미 수집 중)이나 PD를 거쳐 들어온다 | 개인 DM으로 온 요청은 기록 밖에 남는다 | DM으로 요청이 오는 경로가 있는지 PD에게 확인 |
| 대표 본인의 범위 결정도 날짜·태그에 반영된다 | 아무도 일정을 지키지 않는다 | 대표 결정 |
