# 업무현황 대시보드 UI 개선 PRD

작성일: 2026-09-10 · 최종 검토일: 2026-09-11 · 버전: 1.0 · 상태: 조사·문서 검증을 마친 최종 제안

이 문서의 산출물은 UI 개선 요구사항이다. 제품 UI 구현·배포·데이터 재수집은 이번 작업에 포함하지 않았다. 아래 성공 수치는 **달성 결과가 아니라 향후 사용자 검증의 목표**다.

## 1. 목적과 핵심 성공조건

### 목적

대표가 여러 프로젝트의 현황을 읽고 **지금 확인하거나 결정해야 할 일, 그 이유, 믿을 수 있는 근거**를 빠르게 찾도록 한다. 프로젝트 책임자는 같은 근거를 확인하고 원본 업무 도구에서 후속 조치를 할 수 있어야 한다.

권고 방향은 **현재의 결정 우선 브리핑을 유지하면서 요약에서 근거로 이동하는 거리를 줄이고, 데이터 상태와 탐색 맥락을 일관되게 보여주는 개선**이다. 기존 화면을 전면 교체할 필요는 없다.

### 제품 성공조건

| ID | 성공조건 | 목표와 측정 방법 |
|---|---|---|
| S1 | 무엇을 먼저 확인할지 이해한다 | 동일 난도의 시나리오에서 5명 중 4명 이상이 30초 이내에 우선 확인 안건 1개와 이유를 맞힌다. 결정 안건이 없으면 신뢰 제한·확인할 위험 또는 ‘이번 분석에 추가 안건이 기록되지 않음’을 실제 데이터에 맞게 답한다. |
| S2 | 연결 가능한 근거와 프로젝트 맥락을 정확히 찾는다 | 직접 근거 계약이 있는 상위 작업·출처 확인 후보는 항목 요약에서 원문 링크 활성화까지 주요 조작 2회 이하. 5명 중 4명 이상이 도움 없이 20초 이내 올바른 근거를 찾는다. 대표 결정·위험은 확인된 프로젝트 맥락으로 1회 이내 이동하며 이를 직접 근거로 표시하지 않는다. 연결이 없으면 같은 위치에서 알 수 있어야 한다. |
| S3 | 확인 불가를 정상으로 오해하지 않는다 | 실패·미실행·부분 분석·과거 분석·필터 0건을 포함한 이해 과제에서 5명 모두 ‘문제 없음’과 ‘확인 불가’를 구분한다. 자동 상태 시나리오도 전부 통과해야 한다. |
| S4 | 탐색·공유 맥락이 유지된다 | 같은 스냅샷에서 필터 적용 → 공유 링크 열기, 상세 진입 → 뒤로 가기의 필터·정렬·대상 일치율 100%. 키보드 필터 변경 후 초점 손실 0건. |
| S5 | 작은 화면에서도 판단과 조작이 가능하다 | 320·375·768·1440 CSS px에서 핵심 정보 유실과 페이지 가로 넘침 0건. 기본 375×812 화면에서 첫 판단 영역의 제목과 첫 안건 또는 상태 설명이 스크롤 전에 보인다. 라이트·다크 모두 핵심 경로를 키보드로 완료한다. |
| S6 | 기존 사실·업무 경계가 보존된다 | 같은 입력의 규칙 판정·대상 ID·집계값이 UI 개선 전후 동일하다. 분석 실패 폴백, 출처 구분, 기존 공유 링크가 회귀 테스트를 통과하고 UI가 결정 저장·Notion 수정·Slack 발송을 추가하지 않는다. |

30초·20초·조작 2회·5명은 프로젝트의 초기 설계 목표이며 업계 평균이나 통계적 유효성이 입증된 기준이 아니다. 기준선은 구현 전에 측정하고, 수치 달성 여부와 실제 판단의 정확도를 함께 본다. 조작 횟수에는 클릭·터치·Enter로 여는 동작을 포함하며 스크롤과 키보드 Tab 이동은 시간에 반영한다. 외부 도구 로그인 시간은 별도로 기록한다.

조사 초기의 ‘모든 안건에서 근거까지 두 단계’ 목표는 현재 데이터 계약으로 보장할 수 없어 위 S2처럼 대상을 구분했다. 대표 결정에 직접 근거를 추가하려면 분석 데이터 계약 변경이 필요하며 이번 UI 범위에 포함하지 않는다. 항목 요약에 도착하기까지의 전체 탐색 시간도 별도로 기록해 국소적인 조작 단축을 전체 흐름 개선으로 과장하지 않는다.

### 이번 PRD의 완료조건

1. 현재 구현, 관찰한 문제, 아직 검증하지 않은 가설을 구분한다.
2. 공식 원칙·제품 사례를 조사하고 적용할 부분과 적용하지 않을 부분을 설명한다.
3. 선택한 접근법, 우선순위, 데이터 제약, 범위 제외를 명시한다.
4. 모든 필수 요구에 수용기준과 검증 시나리오를 연결한다.
5. 독립 검토에서 발견한 모순·누락을 수정하고, 제품 효과를 검증한 것처럼 쓰지 않는다.

## 2. 대상 사용자와 사용 맥락

| 사용자 | 주요 상황 | 해야 할 판단 | 화면이 제공할 결과 |

| 대표, 1차 사용자 | 하루 첫 업무 확인, 프로젝트 회의 직전 | 오늘 어떤 선택·승인·확인이 필요한가? | 안건, 이유, 관련 프로젝트, 근거, 판단 제한 |

| 팀장·작업 담당자, 보조 사용자 | 공유받은 확인 목록 점검 | 내 범위에 어떤 관리 누락이 있고 어디서 고치는가? | 필터가 유지된 목록, 수정 방법, 원본 링크 |

대표 중심이라는 근거는 [README](/Volumes/PortableSSD/newtaskdashboard/README.md)와 [기능 적합성 결정](/Volumes/PortableSSD/newtaskdashboard/FEATURE-REVIEW-DECISIONS.md)에 있다. 실제 사용 빈도, 평균 검토 시간, 모바일 비율은 아직 확보하지 않았다. 대표의 아침 브리핑과 책임자의 후속 확인을 우선 시나리오로 채택하되, 개인 성과 평가나 실시간 관제 수요는 추정하지 않는다.

대표적인 흐름은 `브리핑 → 안건 근거 확인 → 필요하면 프로젝트 맥락 확인 → 원본 도구에서 후속 처리`다. 대시보드는 앞의 세 단계를 돕고, 마지막 단계의 처리 결과는 이후 수집값으로 확인한다.

## 3. 조사 범위와 현재 상태

### 조사 기준

- 기준 제품: 현재 작업 트리의 `public/` UI와 연결된 모델·표현 함수. `decision-dashboard.html` 같은 과거 시안은 현행 화면으로 취급하지 않았다.
- 기존 미커밋 UI 변경과 [가독성 개선 기록](/Volumes/PortableSSD/newtaskdashboard/docs/readability-plan.md)을 포함한 현재 상태를 출발점으로 삼았다. 해당 기록의 과거 테스트 결과를 이번 실행 결과로 사용하지 않았다.
- 브라우저 관찰: 기존 파일과 저장 데이터만 제공하는 로컬 읽기 전용 미리보기. 자동 스케줄러·수집·외부 쓰기는 실행하지 않았다.
- 관찰 데이터: `data/dashboard.json`, 생성 시각 2026-08-07 21:13 KST, 프로젝트 객체 6개. 이 시점의 업무 수치와 이슈는 현재 업무 상태를 의미하지 않는다.
- 외부 자료는 2026-09-10에 확인했다. 고객 인터뷰·운영 사용 로그·정식 사용성 테스트는 수행하지 않았다.

### 이미 구현된 기능: 유지할 자산

현재 네 메뉴는 `브리핑 / 프로젝트 / 담당자 / 확인필요`다. 브리핑은 결정 요청 다음에 **에이전트 통합 분석**을 두고, 그 안에 프로젝트 현황 브리핑을 포함한다. 프로젝트 현황 브리핑은 현재 진행·빌드·출시·데이터·실행 병목·확인 필요·다음 주요 행동과 프로젝트별 최신 상태를 함께 보여준다. 에이전트가 표시한 위험 신호도 이 현황 브리핑 안에서 현재 진행에 영향을 줄 수 있는 확인 신호로 설명하며, 확정 장애·관리 데이터 오류·출처 확인 후보와 구분한다. 분석의 실패·미실행·부분·과거 상태, 원문 링크·복사, 프로젝트 이동, 담당자·확인필요 필터, 모바일 작업 정보 보존도 이미 존재한다. 이를 신규 기능으로 다시 만들지 않는다. ## 4. 필요한 도메인 지식과 사례 조사

### 제품 도메인의 해석 규칙

1. **프로젝트 진행, 관리 데이터 품질, 분석 신뢰도는 서로 다르다.** 날짜 미입력 건수가 많다는 이유만으로 사업 일정이 위험하다고 단정할 수 없다. 같은 색과 같은 ‘위험’ 이름으로 합치지 않는다.
2. **Notion은 공식 계획·상태의 기준이고, Slack·회의록·Git은 보조 근거다.** 출처 간 주장이 다르면 병렬로 보여준다. Git 활동량으로 완료·생산성을 추정하지 않는다.
3. **규칙 사실, 에이전트 분석, 출처 확인 후보는 다른 확실성을 가진다.** 확인 후보를 대표 결정이나 확정 병목으로 자동 승격하지 않는다.
4. **정보가 없다는 것은 문제가 없다는 뜻이 아니다.** 미수집·부분 수집·오래된 분석·비교 기준 없음의 상태를 콘텐츠와 함께 보여준다.
5. **작업 수와 완료율에는 분모가 있다.** 현재 필터 범위, 제외 상태, 중복 여부를 명시한다. 담당자별 건수는 작업량 참고이며 성과·시간·과부하 지표가 아니다.
6. **읽기 전용 UI의 행동은 탐색과 원본 이동이다.** 완료 체크·승인 저장을 붙이면 상태 동기화와 감사 이력까지 별도 설계해야 하므로 이번 범위를 벗어난다.

## 5. 접근법 선택

| 후보 | 장점 | 비용·문제 | 판단 |
|---|---|---|---|
| A. 색·그림자·카드 모양 중심의 시각 개선 | 변경 범위가 작고 미적 일관성을 정리하기 쉽다 | 필터 공유, 상태 오해, 근거 이동 문제를 해결하지 못한다 | 보조 작업으로만 채택 |
| B. 기존 구조를 유지하고 판단 정보·근거 탐색·상태 표현을 개선 | 관찰된 문제와 직접 연결되고 현행 모델·테스트를 재사용한다 | 데이터가 없는 진행·근거는 UI만으로 채울 수 없다 | **선택** |
| C. 그래프·칸반·자동 우선순위 중심의 전면 개편 | 다른 관점의 탐색을 제공할 수 있다 | 새 정보 구조·판정·데이터 계약이 필요하며 대표의 첫 판단에 대한 이점이 미확인이다 | 제외 |

선택 기준은 S1–S6 기여도, 현재 근거의 확실성, 기존 작업 재사용, 범위의 가역성이다. 정량 사용자 자료가 없는 상태에서 임의의 ROI 점수나 완료 예상일은 산출하지 않았다.

핵심 설계는 **‘판단 요약’과 ‘근거 상세’의 두 수준**이다. 기존 프로젝트 계층은 전체 탐색을 위해 유지하지만, 직접 근거가 연결된 항목을 확인할 때는 불필요한 추가 펼침을 줄인다. 대표 결정은 현재 계약대로 프로젝트 맥락을 통해 확인한다. 별도 전역 사이드 패널이나 새 메뉴를 만드는 것보다 기존 카드·링크·URL 상태를 우선 확장한다.

## 6. 목표 화면과 정보 위계

### 브리핑

| 순서 | 기본 노출 | 상세에서 노출 |
|---|---|---|
| 1. 대표가 확인할 판단 | 안건, 프로젝트, 이유와 맥락에 이미 명시된 기한·영향, 프로젝트 맥락 동작 | 프로젝트 내부의 근거 탐색. 안건별 직접 출처는 현행 계약에서 미지원 |
| 2. 데이터 신뢰 확인 | 출처별 수집 상태, 분석 최신성, 판단 제한과 해석 기준 | 출처별 성공 시각, 실패 이유, 운영 오류 원문 |
| 3. 현재 관리상 막힌 것 | 규칙 엔진이 감지한 작업·구조·연동 문제를 하나의 수정 큐로 묶고, 원인·영향·담당자·수정 경로를 보여준다. | 항목별 세부 규칙, 원본 작업, 수정 경로 |
| 4. 어제와 달라진 것 | 비교 기준 시각과 동일 필드의 변경 전·후 | 나머지 변화, 관련 대상 이동 |
| 5. 출처 확인 후보 | 후보 수와 ‘미검증’ 성격 | 현재와 같이 후보 근거를 펼침 |
| 6. 관리 점검 | 현재 5개 KPI와 중복·집계 범위 설명 | 필터된 대상 목록과 원본 수정 경로 |

상단에는 신뢰를 판독할 수 있는 정보를 남기되 같은 원인의 오류 배너·출처 상세·분석 설명을 반복하지 않는다. 수집 실패와 분석 실패는 서로 다른 사건일 수 있으므로 무조건 하나로 합치지 않는다. 판단을 막는 오류는 접힌 로그 안에만 두지 않는다.

결정·위험이 0건이면 큰 빈 카드를 유지하는 대신 제한 이유를 포함한 간결한 상태 행으로 바꿀 수 있다. 정상 성공 0건과 실패 때문에 표시할 수 없는 상태의 제목·문구는 다르게 한다.

### 프로젝트·담당자·확인필요

- **프로젝트:** 접힌 항목에 프로젝트명, 출처가 있는 현재 진행의 한 문장, 다음 완료 지점 또는 ‘근거 없음’을 우선한다. ‘관리 점검: 12개’는 별도 보조 정보로 둔다. ‘관리 오류’를 사업적 건강 상태처럼 보이게 하지 않는다.
- **담당자:** 기존 필터·정렬을 유지하고 적용 범위·초점·뒤로 가기 상태를 일관되게 한다. 작업 수를 성과 점수로 강조하지 않는다. 미배정 작업은 사람에게 임의 귀속하지 않는다.
- **확인필요:** 필터 범위와 결과 수를 함께 보여준다. 현재의 대상별 묶음과 수정 방법을 유지한다. 원본 이동·목록 복사·조건 초기화가 구분돼야 한다.

에이전트 통합 분석은 1번 대표 판단 아래에서 프로젝트 현황 브리핑을 감싸는 요약 수준이다. 현황 브리핑 안에서는 여섯 관점과 분석 위험 신호를 같은 프로젝트 맥락으로 읽고, 3번 관리상 막힌 것에서는 규칙 엔진이 확인한 데이터·구조·연동 문제를 분리한다. 화면 폭을 채우기 위해 빈 카드를 늘리거나 단순한 숫자를 장식 차트로 바꾸지 않는다.

## 7. 요구사항과 수용기준

P0는 첫 개선 릴리스의 필수 범위, P1은 P0 검증 이후의 두 번째 범위다. ‘유지’는 기존 기능의 회귀 방지, ‘개선’은 현행 동작의 보완, ‘확장’은 새 UI 동작을 뜻한다.

### F1. 신뢰·빈 상태를 콘텐츠 가까이 표시 [P0 · 개선]

- 데이터 기준 시각과 분석 시각을 구분하고 한국 시간으로 표시한다. 기존 36시간·입력 스냅샷 비교의 최신성 판정을 변경하지 않는다.
- 결정·위험·확인필요 각각에서 ‘0건’, ‘조건 일치 없음’, ‘분석 불가/제한’을 구분한다.
- 전일 비교가 없으면 변화 0건을 정상 비교 결과처럼 설명하지 않는다.
- 관리 상세를 펼치기 전에도 현재 판단의 유효 범위를 알 수 있다.

**수용기준:** T1–T4의 모든 상태에서 원인에 맞는 제목·설명·다음 동작이 표시된다. 실패·미실행일 때 과거 분석 문장이 정상 최신 분석으로 노출되지 않는다. 부분·과거 분석은 제한 표시와 함께 기존 허용 범위대로 유지한다. 연결: O1·O6, S1·S3·S6.

### F2. 요약에서 정확한 대상·근거로 이동 [P0 · 개선/확장]

- 결정·위험의 기존 프로젝트 이동은 유지하고 동작명을 ‘프로젝트 맥락 보기’로 명확히 한다. 구조화된 직접 근거 필드가 없는 이 두 유형에 `evidenceUrl`·`specId`를 임의로 추가하지 않는다.
- 이미 직접 근거가 있는 상위 작업·출처 확인 후보는 항목 요약 옆에 원문 또는 근거 상세 진입을 제공한다. 현재 데이터의 정확한 ID·URL만 사용한다.
- 진행 중 프로젝트 KPI의 각 항목에 해당 프로젝트로 이동하는 명시적 동작을 추가한다.
- 근거 상세는 출처 이름, 자료 시각, 관련 발췌, 원문 링크를 함께 제공한다. 제목 문자열 유사도만으로 작업을 연결하지 않는다.
- 원문은 새 탭에서 열고 대시보드 맥락을 유지한다. 프로젝트 상세에서 돌아오면 출발 안건과 필터를 복원한다.

**수용기준:** 현행 스키마에 유효한 상위 작업·출처 후보 fixture에서 항목 요약 → 원문 활성화가 2회 이하이고 정확한 ID·URL에 도달한다. 결정·위험·프로젝트 KPI는 연결된 프로젝트로 1회 이내 이동한다. 프로젝트 수준 연결만 있으면 ‘프로젝트 맥락 보기’, 직접 원문이 없으면 ‘연결된 원문 없음’으로 표시한다. 프로젝트 화면으로 이동한 것만으로 직접 근거 확인 성공으로 집계하지 않는다. 연결: O3·O7, S2·S4·S6.

### F3. 필터·공유·뒤로 가기의 범위를 일치 [P0 · 개선]

- 확인필요 URL에 프로젝트·팀·담당자·분류·문제 유형을 모두 보존한다. 기존 URL도 계속 해석한다.
- 필터를 바꾼 뒤 동일 컨트롤에 초점을 유지하고 결과 수만 정중한 상태 알림으로 안내한다. 결과 목록 첫 행으로 강제 이동하지 않는다.
- 적용 중인 조건과 필터 결과 수를 항상 보여주고 전체 초기화를 제공한다. 0건에서는 조건 초기화가 가장 가까운 동작이다.
- 뒤로 가기·다시 열기에서 사용자가 보고 있던 목록 범위와 선택 대상을 복원한다. 상세 이동은 브라우저 히스토리에 남기고 연속 필터 변경은 히스토리를 과도하게 늘리지 않는다.
- 프로젝트·담당자의 현재 필터와 정렬도 새로고침·뒤로 가기에서 유지한다. P0 공유 일치 보장은 현재 복사 기능이 있는 브리핑·확인필요에 적용하고, 새 공유 버튼 신설은 요구하지 않는다.

**수용기준:** T5·T6·T7 통과. 같은 스냅샷에서 공유 전후 대상 ID 집합이 동일하다. 다른 시각의 스냅샷이면 조건은 같게 복원하되 수집 기준 시각을 보여주며 과거 목록의 동일성을 약속하지 않는다. 없는 필터 값은 조용히 ‘전체’로 확대하지 않고 해당 조건·0건·초기화 안내를 보여준다. 연결: O4·O5·O6, S3·S4.

**상태 복원 범위:** T11에서 아래 계약도 검증한다. 공유 URL을 열 때 해당 메뉴의 URL 조건이 기존 로컬 상태보다 우선하며, 공유 가능한 조건 중 URL에서 생략한 값은 기본값으로 해석한다. 다른 사용자의 과거 필터가 공유 목록에 섞이지 않아야 한다. 같은 탭의 내부 뒤로 가기는 해당 히스토리 시점의 상태를 복원한다.

| 화면 | 공유 URL로 복원할 상태 | 새로고침·내부 뒤로 가기에서 복원할 상태 |
|---|---|---|
| 브리핑 | KPI 상세, 프로젝트·팀·담당자 조건 | 왼쪽 상태와 출발 항목·스크롤 위치 |
| 확인필요 | 프로젝트·팀·담당자·분류·문제 유형 | 왼쪽 상태와 열려 있던 대상·스크롤 위치 |

### F4. 첫 화면 공간과 조작 가독성 개선 [P0 · 개선/유지]

- 중복 안내를 줄이고 0건 영역의 여백을 축소해 첫 판단을 앞당긴다. 모든 분석·실패 정보를 접는 방식은 사용하지 않는다.
- 안건 제목·핵심 이유·제한 문구를 주요 텍스트로, 시각·출처 수·보조 수치를 메타로 구분한다. 긴 한국어·URL은 줄바꿈하고 핵심 문장을 말줄임표만으로 숨기지 않는다.
- 상태색은 의미 전달용으로 사용하고 상태 텍스트를 함께 둔다. 원문·복사·펼침은 정지 상태에서도 동작임을 알 수 있어야 한다.
- 기존 테마·시스템 글꼴·토큰을 기반으로 한다. 본문은 14–16px 범위, 메타는 12px 이상을 초기 시안의 제안값으로 삼되 화면 검증 후 하나의 스케일로 확정한다.
- 본문 대비 4.5:1 이상, 큰 텍스트 3:1 이상. 비인라인 조작 대상은 24×24 CSS px 또는 기준의 간격 조건을 충족하고 모바일 주요 버튼 높이는 44px 이상을 제품 목표로 한다. 키보드 초점은 보이고 고정 영역에 가려지지 않는다.

**수용기준:** T8 통과. 375×812 기본 화면의 ‘결정 있음·최신’, ‘결정 없음·과거’, ‘분석 실패’ fixture에서 첫 판단 제목과 첫 안건/상태 설명이 보인다. 안건 전문과 추가 제한은 자연스러운 세로 스크롤로 읽는다. 글자를 줄여 높이 목표를 맞추지 않는다. 연결: O1·O8, S1·S5.

### F5. 프로젝트 현황과 목록의 진행 맥락 강화 [P1 · 개선]

- 브리핑 상단에 프로젝트 현황 브리핑을 노출해 프로젝트별 현재 상태·진척·관리 확인 항목을 한 곳에서 비교할 수 있게 한다. 각 행은 기존 프로젝트 상세로 이동한다.
- 접힌 프로젝트에 기존 데이터가 뒷받침하는 현재 진행·다음 완료 지점을 제공한다. 필드가 없으면 ‘현재 진행 요약 없음’ 또는 ‘다음 완료 지점 미확인’으로 표시한다.
- 자유문 요약을 임의로 ‘제작 중·QA·출시’ 같은 확정 단계로 재분류하지 않는다. 긴 요약은 원문 의미를 보존한 미리보기와 전문 보기로 제공한다.
- 관리 문제 건수와 프로젝트의 진행·분석 상태를 명칭과 배치로 분리한다. 기존 기본 정렬을 유지한다면 ‘관리 확인 많은 순’처럼 실제 기준을 표시한다.
- 기존 스프린트 완료율의 분자·분모와 종료 상태 포함 여부를 안내한다. 계산식 변경이나 완료율을 이용한 새 건강 점수는 포함하지 않는다.

**수용기준:** T9에서 사용자가 브리핑과 프로젝트 목록의 진행 정보, 관리 점검을 구분한다. 모든 문장이 기존 프로젝트/상위 작업 데이터로 추적되고 값이 없으면 미확인 상태를 표시한다. 단계·다음 완료 지점이 구조화되지 않은 프로젝트에서도 추정값을 만들지 않는다. 연결: O2·O3, S1·S2·S6.

### F6. 디자인 기준 문서 정합성 확보 [P0 준비 작업 · 문서]

단계 0에서 현재 구현과 STYLESEED의 충돌 목록을 만들고, 단계 1에서 채택할 시안과 일치하는 대체 디자인 기준 및 교체 조항 목록을 확정한다. **시각 구현은 대체 기준을 STYLESEED에 반영한 뒤 시작한다.** 이번 PRD는 레이아웃·타입의 변경 제안이며 기존 디자인 락을 이미 변경했다는 뜻은 아니다. 브랜드·상태색 의미·테마 토큰은 유지하고, 이번 목적에 필요한 배치·밀도·타입 규칙만 새 기준으로 명확히 교체한다.

**수용기준:** T12에서 구현에 적용할 팔레트·타입·간격·표면·상태·펼침 규칙이 한 문서에서 모순 없이 해석됨을 확인한다. 채택한 시안과 기준이 일치하며 오래된 벤토 배치로 되돌리는 회귀가 없다. 연결: O8, S5·S6.

**확인된 제약과 F2 선행 확인:** [분석 스키마](/Volumes/PortableSSD/newtaskdashboard/schemas/agent-analysis.schema.json:67)에서 대표 결정의 추가 속성을 금지하고 위험을 문자열로 정의한다. 결정·위험의 직접 근거 계약이 없다는 점은 미확정 가설이 아니라 확인된 사실이다. 상위 작업·출처 후보의 실제 URL 연결 비율과 결정·위험의 정확한 프로젝트 연결 비율은 유형별로 측정한다. 시험 데이터도 현행 스키마를 통과해야 한다.

직접 연결이 없는 항목은 원문 접근 시간의 분모에서 제외하되, 전체 대상 중 ‘근거 없음’ 비율과 전체 탐색 시간을 함께 보고한다. 유형을 섞거나 유리한 fixture만 골라 성공을 과장하지 않는다. 상위 작업·출처 후보조차 실제 계약으로 S2를 시험할 수 없으면 S2는 미달/보류로 보고한다. 대표 결정의 직접 원문 연결이 추후 필수로 확인되면 별도 데이터 계약 변경 범위를 정의하고, 이번 P0 성과로 포함하지 않는다.

예상 구현 접점은 [app.js](/Volumes/PortableSSD/newtaskdashboard/public/app.js), [dashboard-presenters.js](/Volumes/PortableSSD/newtaskdashboard/public/dashboard-presenters.js), [dashboard-management.js](/Volumes/PortableSSD/newtaskdashboard/public/dashboard-management.js), [dashboard-view-model.js](/Volumes/PortableSSD/newtaskdashboard/public/dashboard-view-model.js), [style.css](/Volumes/PortableSSD/newtaskdashboard/public/style.css)다. 이 파일들은 이번 문서 작성에서 수정하지 않았다.

## 10. 범위 제외와 유지 조건

- Notion 쓰기, 결정 승인·저장, Slack 메시지 발송, 알림 구독, 자동 처리 완료.
- 새 커넥터·패키지·프레임워크·유료 API·커스텀 폰트 도입.
- 위험 판정, 최신성 임계값, 수집 주기, 완료율 계산식 변경.
- 개인 생산성 점수, 과부하 추정, 제거된 팀 대기 영향도 복구.
- 새로운 예측 차트·칸반·전사 검색·처리 이력 원장·권한 체계 구현.
- 운영 배포와 운영 데이터 갱신. 운영 공개 범위는 별도 검토 대상이며 이 PRD가 배포 승인을 대신하지 않는다.

현재 원문 링크·복사·담당자 필터·스프린트 구조·샘플 표시·실패 폴백을 유지한다. ‘단순화’는 정보 누락이나 규칙 변경이 아니라 반복 안내, 불필요한 펼침, 범위 재설정의 감소를 뜻한다.

### 사용자 검증 방법

1. 대표 역할 1명 이상, 프로젝트 책임자 2명 이상, 후속 확인 담당자를 포함해 총 5명을 모집한다. 동일인이 역할을 겸하면 실제 구성과 한계를 적는다.
2. 현행과 개선 시안에 같은 난도의 데이터 2세트를 사용하고 순서를 교차 배정한다. 안건·근거 정답은 시험 전에 지정한다. 개인·프로젝트 이름은 시험용으로 대체할 수 있다.
3. ‘우선 확인할 것과 이유’, ‘안건의 근거 찾기’, ‘이 상태를 믿어도 되는지 설명’, ‘공유 목록 재확인’을 수행한다. 힌트 없이 진행하고 정답·오해·시간·조작 수·되돌아감을 기록한다.
4. S1–S4 기준선과 개선값을 함께 보고한다. 5명 표본으로 전 사용자에 대한 인과 효과나 유의성을 주장하지 않는다.
5. 오해 1건이라도 발생한 신뢰 상태는 원인 문구·배치를 수정해 재시험한다. 다른 안건을 찾게 한 탐색 오류도 P0 결함으로 다룬다.

첫 검증에는 외부 분석 SDK가 필요 없다. 관찰 기록으로 `scenario_id, variant, role, correct, elapsed_seconds, action_count, interpretation_error`를 남기고 업무 원문·직원별 평가 데이터를 불필요하게 저장하지 않는다.

### 구현 이후 기술 검증

관련 회귀 테스트 → `npm test` → `npm run build` → `git diff --check` → 실제 브라우저 시나리오 순으로 검증한다. 현재 package.json에는 별도 lint·typecheck 명령이 없으므로 실행하지 않은 검사를 통과했다고 보고하지 않는다. 기존 테스트 실패가 있으면 이번 변경 영향과 분리해 원인을 기록한다.

### 독립 검토 반영 · 2026-09-11

독립 리뷰 2회에서 보완점 5개를 확인해 수정했다.

1. 결정·위험에 직접 근거 필드가 없다는 스키마 제약을 명시하고 S2를 ‘기존 직접 근거 접근’과 ‘프로젝트 맥락 이동’으로 구분했다. 스키마 밖의 fixture로 성공을 만들지 않으며 시험 불가 시 부분 릴리스로 보고한다.
2. 최신성 미확인 상태를 원래 성공/부분의 시각 미상, 인식 불가 원상태로 나누고 이전 형식도 별도 문구·본문 규칙으로 분리했다.
3. 브리핑 공유와 프로젝트·담당자의 내부 필터·정렬 복원까지 T5·T11에 추가했다. URL과 로컬 상태의 우선순위를 명시했다.
4. 대체 디자인 기준과 교체 조항을 시각 구현 전 확정·반영하는 순서로 통일하고 T12를 추가했다.
5. T1의 결정 개수를 현행 스키마에 맞는 0·1·5개로 한정했다. 계약 밖 데이터를 성공조건 측정에 사용하지 않는다.

문서 자체는 로컬 Markdown 렌더링에서 제목·표 구조를 확인하고 링크 대상 존재 여부·표 열 정합성을 검사했다. 제품 효과, 전체 회귀, 양 테마 전체 접근성 검증은 향후 구현 단계의 작업이다.
