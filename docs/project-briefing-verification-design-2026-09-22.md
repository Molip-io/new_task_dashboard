### 요구사항에서 시작하는 작성 절차

에이전트는 문장을 쓰기 전에 허용된 근거로 다음 항목을 내부적으로 정리한다. 새 JSON 필드를 임의 추가하는 지시가 아니다.

1. 현재 전달/배포 상태: 스프린트, 빌드 버전, 플랫폼, 전달 대상/스토어, 실제 전달·배포 사건 날짜, 현재 유효한 상태, 근거. 파트너 전달본·스토어 배포본이 다르면 각각 구분한다. 최신 날짜의 빌드 언급을 현재 배포본으로 취급하지 않는다.
2. 다음 빌드 상태: 스프린트, 목표 버전(불명이면 불명), 준비/개발/내부 테스트/QA/제출 단계, 합의된 남은 일, 명시된 일정, 근거. 최신 후보가 기존 전달본의 기록을 지우지 않는다.
3. 빌드 성과: 해당 버전·플랫폼·기간·코호트의 D1/RV 등 실측 결과 또는 명시적 A/B 판정. 데이터 품질 사건은 별도 제한으로 분리한다.
4. 취소·보류·재배포·부분 배포 사건을 시간순 대조한다. 부분 배포 취소를 기존 사용자 전원 롤백이나 이전 버전 복귀로 추정하지 않는다.
5. 이 사실 정리가 끝난 뒤 buildRelease를 '현재 나간 빌드 → 다음 나갈 빌드 → 다음 단계'의 짧은 자연어 문장으로 작성한다. 근거 없이 빈칸을 채우거나 예시 버전을 상수로 넣지 않는다.

일반 작업의 활성/완료 제외 규칙과 프로젝트 출시 이력 근거를 구분한다. 완료된 빌드 전달 기록은 활성 업무·지표 집계로 되살리지 않으면서도 마지막 전달 상태의 근거로 쓸 수 있어야 한다. 현재 지침의 완료 업무 전면 제외·스펙 우선 심층 대조 제한이 이 확인까지 막지 않도록 범위를 명확히 분리한다.

### 근거가 부족할 때의 처리

latestBuild/latestRelease/latestData를 확정 답으로 사용하지 않는다. 허용 프로젝트의 이미 연결된 릴리스·전달 스레드, 회의록, 성과 리포트를 우선 확인한다. 프로젝트 운영 근거 확인은 specId=null이어도 허용하며 스펙 3개 심층 대조 한도와 별도로 작은 조회 예산을 명시한다. 최근 7일 일반 검색을 무제한 확장하지 않고, 이전 마지막 전달 기록과 해당 버전의 후속 취소·갱신 기록을 추적한다.

현재 전달본이 끝내 확인되지 않으면 '현재 외부 전달 빌드는 확인되지 않았습니다. 다음 SP3.5 빌드는 내부 테스트 중입니다'처럼 확인된 축과 불명인 축을 분리한다. '현재 빌드가 없다'라고 결론내리지 않는다. 성과 근거가 없으면 data=null이다. 이때 UI는 '해당 빌드의 성과 지표 미확인'만 표시하며 수집 상태나 로그 오류로 빈자리를 채우지 않는다. 성과값이 일부 확인되면 그 값은 보존하고 불명 조건을 별도로 명시한다.

### 지침·실행문·화면의 책임

- 지침: 기존 끝부분에 보정 규칙을 계속 추가하지 않고, 프로젝트 브리핑 규칙을 한 본문으로 통합한다. currentProgress는 프로젝트 전체, buildRelease는 현재/다음 빌드, data는 실측 성과, blockers는 실행 차단, nextActions는 합의 행동/AI 제안으로 정의한다. 기존 수치·스펙·deltas 계약은 보존한다.
- 매일 실행문: 입력 검증 → 프로젝트별 현재/다음 빌드와 지표 근거 확인 → 통합 요약 → 의미 검증 → 저장/재조회 검증 순서로 단일화한다. 요약 초안에 입력 근거 문단을 복사하는 단계를 두지 않는다.
- 확인필요: 프로젝트 브리핑 UI에서 완전히 제거한다. 현재 스키마가 confirmationRequired를 필수로 요구하므로 전환기 출력은 []로 유지하고 UI에서는 읽지 않는다. 이후 버전 변경 때 스키마에서 제거한다. 앱의 기존 '확인필요' 탭과 스프린트 가이드 지표를 삭제하라는 뜻은 아니다.
- 불확실성: 해당 상태에 짧게 표시하고 분석 제한으로 남긴다. 모든 불확실성을 nextActions의 확인 요청으로 옮기지 않는다. 업무상 필요한 근거 있는 행동만 남긴다.
- 화면: buildRelease와 data를 분석 JSON에서 그대로 표시하고 원문은 접힌 출처로 보낸다. sourceHealth는 AI 통합 브리핑의 수집 상태 영역에서만 사용한다. 샘플로 자동 대체하는 경로도 별도 수정 대상이다.
- 입력 고정: 단순 후속 갱신과 양립 불가능한 입력을 구별한다. 같은 실행 ID라는 이유로 합치거나, 생성 시각만 다르다는 이유로 분석을 실패시키지 않는다. 미제공 inputHash를 필수 필드로 요구하지 않는다. 현 스키마에서는 기준 pageId/runId/generatedAt 및 제한을 허용된 confidenceLimits 문자열/보고에 기록하고, 새 추적 필드는 수집기·스키마·독자를 함께 변경할 때 도입한다.
- 에이전트는 스냅샷 선택·UI 표시·배포 완료를 통제하지 못한다. 이 책임을 실행문에 요구하지 않는다. 저장 성공과 운영 반영 성공은 구분한다.

- `public/app.js`는 API 응답을 기다리지 못하면 실패 시 샘플 데이터로 대체하는 경로가 있었다. 이번 사용자 화면에서 실제 발생했는지는 미확인이나 운영 데이터 확인을 방해할 수 있는 코드 경로다.
- 동일 runId의 규칙 입력 페이지가 2개다. 본문 generatedAt은 14:19:28과 14:44:20이다. 뒤의 입력에는 새 Slack/Git 근거가 있어 단순 시각 차이만 있는 중복이 아니다. 분석 본문 시각보다 늦다. 분석 notes의 '동일 입력' 설명만으로 어떤 최종 입력을 읽었는지 증명할 수 없다.
- 스냅샷도 동일 날짜 runId가 2개다. 독자는 날짜 내림차순 후 첫 페이지를 택한다. 동일 날짜 중복 선택 기준이 없어 다른 입력 시점이 선택될 위험이 있다. 실제 운영 요청에서 어느 것이 선택됐는지는 미확인이다.

## 핵심 성공조건

1. Notion의 검증된 프로젝트 분석 → API → 화면의 프로젝트명·runId·분석 시각·각 문장이 일치한다.
2. currentProgress에서 하는 일, 확인된 진척, 남은 일, 다음 단계가 이해된다. summary는 그 압축본이다.
3. buildRelease는 마지막 확인된 전달/배포 빌드와 다음 준비 빌드를 구분한다. 스프린트 번호와 빌드 버전, 예정과 완료, 배포 취소와 롤백을 섞지 않는다.
4. data는 대상 빌드와 연결되는 성과·실험 결과만 담는다. 없으면 null이다. 관측되지 않은 수치나 승리 판정을 만들지 않는다.
5. 지침 준수 실패, 입력 변경, 출처 부족, 전송 실패가 서로 구분된다. 오래된 내용이나 샘플을 현재 분석처럼 보여주지 않는다.
6. 입력과 출력의 버전 관계를 재현할 수 있다. 실행 중 재수집이 일어나도 분석 기준이 조용히 바뀌지 않는다.

## 수정 설계와 순서

### 1. 화면의 데이터 연결부터 교정

기존 로컬 변경을 검토·보완하는 것이 먼저다. 추가로 별도 브리핑 생성 로직을 만들지 않는다.

| 화면 | 기준 데이터 | 없을 때 |
|---|---|---|
| 현재 진행 요약 | projectBriefing.currentProgress | 분석 미확인 표시 |
| 빌드·출시 현황 | projectBriefing.buildRelease | 마지막 상태 미확인 표시 |
| 빌드 성과·실험 결과 | projectBriefing.data | 연결된 성과 지표 미확인 표시 |
| 실행 병목 | 해당 프로젝트 blockers | 미확인과 실제 없음 구별 |
| 확인필요 / 판단 전 확인 | 표시 제거 | 전환기 JSON은 confirmationRequired=[] |
| 다음 주요 행동 | projectBriefing.nextActions | 합의 행동과 AI 제안 구별 |

원문 발췌는 접힌 근거 영역으로 보낸다. sourceHealth는 출처/수집 상태에만 사용한다. 기존 스프린트별 업무현황 기능과 수치 계산은 유지한다. 프로젝트 전환 시 해당 프로젝트의 동일 분석 객체를 사용한다.

API 지연/실패 시 로딩·재시도·마지막 성공 데이터의 시점을 보여준다. 샘플은 명시적 demo 모드에서만 사용한다. 타임아웃은 운영 응답시간에 맞춰 정하되 자동 샘플 전환을 제거하는 것이 핵심이다.

### 2. 성과 지표와 데이터 품질을 분리

지침과 실행문을 각각 하나의 기준 문서로 유지하고 같은 규칙을 입력 constraints와 검증에 반영한다. 새 문서를 계속 덧붙이는 방식을 피한다.

- data 허용: 실제 빌드의 D1/D7, RV, ARPDAU, 퍼널, A/B 결과 등. 빌드·플랫폼·관찰 기간·코호트/실험군 및 수치의 단위를 확인한다. 불명인 항목은 불명이라고 쓰고 현재 빌드에 임의 귀속하지 않는다.
- data 제외: 로그 누락, 수집 성공, 음수/이상치 사용자 수, QA 점검 결과만 있는 문단. 이를 confidenceLimits로 이동한다. 실제 의사결정/실험을 막는다는 근거가 있으면 blockers에도 짧게 기록한다.
- 이번 피자레디 결과의 권장값: data=null. 'event_currency 재검증 전 관련 실험 지표의 신뢰도를 확정할 수 없음'을 제한으로 기록한다.
- 수치가 없을 때 재실행만 반복하지 않는다. 허용된 근거에 성과 리포트가 연결됐는지 확인하고, 없다면 지표 리포트의 데이터 연결이 별도 필요하다고 명시한다. 에이전트가 읽지 않은 출처를 읽었다고 주장하지 않는다.
- A/B 수치가 조금 높다는 이유만으로 승리라고 쓰지 않는다. 공식 판정 또는 사전에 정한 판정 기준과 표본/관찰 조건을 확인한다.

단어 포함 여부만으로 의미 검증을 완료했다고 판단하지 않는다. 실제 값·단위·대상·비교 근거가 존재하는지 검사하고 애매하면 제한을 붙인다.

### 3. 빌드 상태는 사건의 흐름으로 요약

Slack 부모 메시지의 날짜와 답글의 날짜·내용을 분리한다. '9/3 오늘 전달'에 새 답글이 달려도 원래 예정일은 9/3이다. 일반 수정 요청이나 피드백 리포트를 전달/출시 완료 사건으로 승격하지 않는다.

관련 빌드의 마지막 확인 사건을 유지하고, 이후 취소·보류·완료·다음 후보의 근거를 대조한다. 최근 7일 조회만으로 그 이전의 마지막 배포 상태를 잃지 않는다. 기존 근거에 마지막 배포 상태가 없다면 미확인으로 명시한다. 버전 숫자를 기준으로 스프린트를 추정하지 않는다.

권장 표시 예시(확인된 14:26 분석 범위):

> 포지 앤 포춘: 9월22일 SP3.5 리뷰용 두 변형 빌드를 비교했습니다. 리프트 유지와 온보딩 수정 후 재테스트하기로 했으며, 최종 제출 빌드와 외부 전달 여부는 아직 확인되지 않았습니다.

> 피자레디: AOS 60.1.0은 9월17~20일 50% 배포 후 취소됐습니다. 다음 재배포 빌드와 QA·스토어 상태는 확인되지 않았습니다.

이는 현재 운영 상태를 새로 확정하는 문구가 아니라 검증된 분석 시점의 표시 예시다.

### 4. 분석 입력 버전을 고정

단기: 중복 입력을 감지하고 pageId·generatedAt·본문의 의미 있는 내용 비교로 기준 입력을 결정한다. 다른 내용이면 '같은 runId이므로 동일'로 간주하지 않는다. 분석 시작 시 읽은 입력을 고정하고 저장 직전에 변경 여부를 확인한다. 변경되면 기존 분석을 해당 시점 결과로 남기고 최신 입력 미반영을 표시한다.

후속 계약 변경: inputRevision/inputHash/sourceCutoff를 입력·출력·스키마·수집기·화면에 함께 도입한다. schema에 필드가 없는데 에이전트만 임의로 추가하지 않는다. 수집 시각 및 previousSummary 같은 파생 값만 바뀐 경우와 실제 업무 근거/규칙/범위가 달라진 경우를 구별한다. revision 산정 대상에 프로젝트 식별·규칙·briefingScope·분석 근거를 포함한다.

입력/스냅샷 발행은 한 실행 주체가 같은 키를 갱신하도록 직렬화하고 upsert 중복을 탐지한다. Notion에 중복이 생겼을 때 임의 첫 페이지를 고르지 않는다. 기존 중복 페이지는 비교 후 기준 페이지를 정하며 검토 없이 삭제하지 않는다.

새 근거가 들어오면 유효한 이전 결과를 숨기거나 성공으로 위장하지 않고 '14:26 분석 · 이후 자료 미반영'으로 보여준다. 자동 갱신 정책은 동일 입력 중복 실행과 무한 재실행을 막아야 한다.

### 5. 프로젝트의 판단 전 확인 제거

사용자 요구에 따라 이 섹션을 제거한다. 불확실성은 해당 상태와 분석 제한에 남기고, 실제 업무에 필요한 행동만 nextActions에 기록한다. 현재 outputSchema를 깨지 않도록 confirmationRequired는 전환기에 []로 유지한다. 다른 화면의 확인필요 탭과 스프린트 관리 지표는 유지한다.

## 구현 후 검증 시나리오

- 같은 runId의 전체/프로젝트 페이지와 API/화면의 currentProgress·buildRelease·data·nextActions가 일치한다.
- 두 프로젝트를 전환해도 내용과 근거가 섞이지 않는다. 기존 스프린트 업무현황 지표는 변하지 않는다.
- 9/3 부모 메시지+9/22 일반 답글이 있을 때 9/3 예정이 9/22 현재 전달 계획으로 표시되지 않는다.
- SP3.5와 빌드3.6을 다른 식별자로 취급하고 APK 공유를 외부 출시로 해석하지 않는다.
- 피자레디 로그 오류만 있는 입력에서 data=null이고 오류는 제한으로 이동한다. 유효한 RV/D1/A/B 근거가 있으면 단위·대상·기간을 보존한다.
- A/B 표본 부족/판정 전 결과에서 승리 그룹을 확정하지 않는다.
- confirmationRequired의 과거 값이 남아 있어도 프로젝트 UI에 확인필요가 나타나지 않고, 프로젝트 요약에 가이드 위반 수가 확인 과제로 자동 삽입되지 않는다.
- 입력이 생성 시각만 달라지면 불필요한 새 분석을 요구하지 않는다. 실제 근거가 달라지면 미반영 상태를 정확히 표시한다.
- 동일 날짜의 입력/스냅샷 중복을 주입했을 때 임의 첫 페이지가 선택되지 않는다.
- API가 8초보다 늦거나 실패해도 샘플로 바뀌지 않는다. 실패 시 재시도 안내를 표시하고, 마지막 성공 결과를 표시할 경우 시점이 명확하다.
- 직접 운영 화면을 다시 열 수 있을 때 실제 URL에서 최종 확인한다. 로컬 테스트·Notion 저장 성공만으로 운영 반영 완료라고 보고하지 않는다.
