# 스프린트별 업무 현황

## 적용 범위

브리핑은 `1. 에이전트 통합 분석 → 2. 어제와 달라진 것 → 3. 스프린트별 업무 현황` 순서다. GPT Agent 설정·스킬·기존 agent-package 파일은 이 변경으로 수정되지 않는다.

프로젝트별 체크박스로 여러 스프린트를 선택한다. 선택은 OR 조건이며 서로 다른 프로젝트의 같은 스프린트 번호를 합쳐 판단하지 않는다. 체크만 하면 조회 미리보기이며, `이 프로젝트 기준 저장`을 누르고 관리자 인증을 해야 팀 공통 현재 스프린트가 바뀐다. 빈 선택은 전체가 아니라 현재 스프린트 없음이다.

## 다섯 지표

공통 범위는 선택된 스프린트에 속한 활성 하위 작업항목이다. 스프린트 미사용 프로젝트는 활성 하위 작업 전체를 포함한다. 완료·일시 정지·정지·중단 항목과 비활성 상위항목 아래 작업은 제외한다.

| 지표 | 정의 |
|---|---|
| 진행 중 프로젝트 | 공통 범위에 활성 작업항목이 하나 이상 있는 프로젝트 수 |
| 진행 중 작업항목 | 공통 범위에서 상태가 정확히 `진행 중`인 항목 수 |
| 기한 초과 작업항목 | 공통 범위에서 원본 `OVERDUE` 또는 양의 초과 일수가 있는 항목 수 |
| 가이드 위반 작업항목 | 공통 범위에 가이드 위반이 하나 이상 있고 기한 초과는 아닌 항목 수 |
| 진행 준비 필요 항목 | 선택된 현재 스프린트에서 `시작 전`이며 기한 초과가 아닌 항목 수. 스프린트 미사용 프로젝트에는 적용하지 않음 |

진행 중은 상태 지표라 기한 초과와 겹칠 수 있다. 준비와 공통 필드 가이드 위반도 겹칠 수 있다. 다섯 숫자를 더해 전체 업무 수로 사용하지 않는다. 기한 초과는 가이드 위반·준비보다 대표 노출을 우선하지만 상세 이슈는 삭제하지 않는다. 상위 작업 관리 문제는 기존 확인필요·감사 데이터에 남는다.

선택 밖 기한 초과와 스프린트 판정 불가 항목은 별도 진입점으로 표시한다. 보기 범위에서 제외됐다고 해결된 것이 아니다.

## 저장과 이전

서버 환경변수 `SPRINT_SETTINGS_TOKEN`에 최소 24자 이상의 무작위 관리자 키를 설정한다. Cron 토큰과 다른 값을 사용한다. 브라우저는 입력한 키를 영속 저장소나 공유 링크에 보관하지 않는다. 키가 없으면 저장은 차단되지만 조회 미리보기는 가능하다.

설정은 기존 Notion 업무현황 요약 DB에 `sprint-settings:` 접두어의 별도 append-only 기록으로 저장한다. 프로젝트 리스트 속성과 원본 업무를 수정하지 않는다. 프로젝트별 첫 저장 전에는 기존 Notion 현재 스프린트를 읽고, 저장 후에는 대시보드 설정을 우선한다. 저장한 빈 배열도 명시적인 설정이다.

배포 후 최초 1회 데이터를 다시 수집해 기존 압축 스냅샷에 없던 안정적인 프로젝트 ID·현재 스프린트 정보를 채운다. 각 프로젝트 설정을 저장하고 다른 브라우저에서 재조회한 뒤에만 Notion의 기존 속성을 숨기거나 제거할 수 있다. 이 PR은 속성을 삭제하지 않는다.

저장 요청은 인증·동일 출처·선택값·예상 버전을 검사하고 저장 후 재조회한다. 버전 충돌을 대부분 감지하지만 Notion은 트랜잭션 CAS 저장소가 아니므로 완전히 동시인 요청을 원자적으로 잠그지는 않는다. 운영자는 중복 편집을 피하고 변경 이력을 확인해야 한다. 현재 이력은 변경 시각과 전후 값이며 개인별 로그인 감사 추적은 포함하지 않는다.

## 분석과의 계약

규칙 엔진은 저장된 설정으로 기존 `currentSprints`와 `sprintRelation`을 구성한다. 원본 `rules.metrics`·감사 행은 유지한다. 브리핑용 집계는 같은 공유 정책 함수로 계산하여 `rules.briefingMetrics`, 집계 단위와 기준은 `rules.briefingScope`로 별도 제공한다. 출력 JSON 스키마는 변경하지 않는다.

스프린트 선택만으로 AI를 재실행하지 않는다. 설정 저장 뒤 기존 수동 재수집을 요청하며, 성공 여부는 수집 상태에서 확인한다. 새 입력 게시 뒤 GPT Agent를 별도 실행해야 한다. 설정이 다르거나 분석 시각이 입력보다 오래됐으면 이전 분석에 갱신 필요를 표시한다. 스프린트 변경으로 숫자가 달라진 것은 업무 진척이 아니다.

전체 활성 specCatalog 분석과 실제 병목 감지는 조회 필터로 줄이지 않는다. 기존 실행문은 현재 Instructions를 참조하면 유지 가능하며, 기존 실행문에 고정된 Notion 현재 스프린트 지시가 있다면 입력의 projects[].currentSprints를 기준으로 바꾼다.

## 검증과 배포 조건

추가 단위 테스트는 `node --test test/sprint-policy.test.mjs test/sprint-settings.test.mjs test/sprint-overview.test.mjs`로 실행한다. 전체 저장소 회귀 검증은 `npm test`와 `npm run build`로 수행한다. 오프라인 Chromium 샘플에서 다중 선택·빈 선택·목록 일치·관리자 입력창·모바일 가로 넘침을 확인했다. 실제 운영 Notion 저장, 자동 수집, GPT 실행과 운영 배포는 별도 검증 대상이다.

기존 웹 UI/일반 API의 접근 정책은 바꾸지 않았으므로 민감한 업무 데이터에 대한 배포 접근 보호를 별도로 확인해야 한다. 변경한 설정 쓰기 API만 별도 인증으로 보호한다.
