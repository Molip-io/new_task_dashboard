# Structured Meeting Evidence

## Purpose

회의록에서 업무 대시보드가 대조에 사용할 **근거만 구조화해 추출**한다. 이 스킬은 프로젝트 상태를 최종 판정하거나 Notion 요약 DB에 직접 저장하지 않는다.

## Inputs

가능하면 다음 입력을 받는다.

- 프로젝트명
- 회의 제목
- 회의 시각
- Notion 원문 URL
- 회의록 본문
- 관련 `analysisTargets`
- 프로젝트의 `specCatalog`

회의록 본문이 없으면 제목만으로 결정·담당자·일정을 추론하지 않는다.

## Extraction Scope

다음 항목만 추출한다.

1. 명시적으로 확정된 결정
2. 실행을 막거나 늦출 수 있는 미해결 쟁점
3. 실제 진행 중이거나 명시적으로 배정된 담당자 작업
4. 명시된 다음 행동
5. 대표 판단이 필요할 가능성이 있는 질문 후보
6. 같은 회의 안에서 서로 충돌하는 발언

프로젝트 상태나 최종 방향 상태는 회의록에 명시적으로 쓰여 있을 때만 `meetingClaim`으로 추출한다. `정상`, `주의`, `개입 필요`를 스스로 판정하지 않는다.

## Evidence Contract

각 항목은 가능한 한 다음 근거를 가진다.

- `specId`, `specTitle`: 회의록에 스펙명·작업항목명·ID가 직접 나타나 안전하게 연결할 수 있을 때만 기록
- `statement`: 추가 해석 없는 짧은 사실
- `owner`: 명시된 경우에만 기록
- `deadline`: 회의에서 명시적으로 합의된 경우에만 기록
- `timestamp`: 회의 시각 또는 기록 시각
- `url`: Notion 회의록 URL
- `excerpt`: 판단을 뒷받침하는 짧은 원문 발췌
- `confidence`: `explicit` 또는 `ambiguous`

근거 URL이나 시각이 없으면 만들지 말고 `null`로 둔다.

## Spec Linking Rules

- 회의록의 스펙명·작업항목명·Notion ID가 `specCatalog` 또는 `analysisTargets`와 직접 일치할 때만 `specId`, `specTitle`을 기록한다.
- 일반 표현이나 유사한 주제만으로 스펙을 추정 연결하지 않는다.
- 여러 스펙이 후보이면 연결하지 않고 `limitations`에 후보가 복수임을 기록한다.
- 한 근거가 여러 스펙을 직접 언급하면 스펙별로 분리하되 같은 원문 발췌와 URL을 보존한다.

## Decision Rules

다음 표현은 명시적 합의가 이어질 때만 확정 결정으로 분류한다.

- 확정, 합의, 진행하기로 함, 담당자 배정, 일정 확정

다음 표현은 기본적으로 미해결 또는 검토 중이다.

- 검토, 논의, 가능성, 의견, 아이디어, 확인 필요, 고려, 우선 시도

작업이 이미 시작됐다는 사실만으로 방향이 확정됐다고 판단하지 않는다.

같은 회의 안에서 앞선 제안 뒤에 명시적인 최종 합의가 있으면 최종 합의를 `confirmedDecision`으로 추출하고 앞선 내용은 필요할 때만 맥락으로 남긴다. 어느 발언이 최종인지 불명확하면 둘 다 보존하고 `ambiguous`로 둔다.

이 규칙은 **같은 회의록 내부**에만 적용한다. Notion 작업 상태, Slack, GitHub 등 다른 출처와 충돌하면 어느 한쪽을 선택하지 않고 상위 에이전트에 양쪽 근거를 전달한다.

## Unresolved Issue Rules

다음을 모두 만족하는 경우만 핵심 미해결 쟁점으로 추출한다.

- 현재 실행을 막거나 늦출 가능성이 있음
- 회의 안에서 닫히지 않음
- 단순 아이디어나 참고사항이 아님

누락된 정보마다 `확인 필요`를 만들지 않는다. 실행에 영향을 주는 누락만 남긴다.

## Owner And Action Rules

- 실제 진행 중이거나 명시적으로 배정된 작업만 기록한다.
- 의견을 말한 사람을 담당자로 추정하지 않는다.
- 담당자가 없으면 `owner: null`로 둔다.
- 행동은 의미를 추가하지 않는 범위에서 실행 단위로 짧게 정리한다.
- 마감일은 회의에서 명시적으로 합의된 경우만 기록한다.

## Executive Decision Candidate Rules

대표 판단 후보는 다음 조건일 때만 추출한다.

- 대표가 답해야 실행 방향이 결정됨
- 우선순위, 출시, 외부 대응, 진행·보류 선택이 필요함
- 파트별 실행이 선택에 따라 달라짐

정보 공유, 단순 보고, 팀 내부 데이터 정정은 대표 판단 후보로 만들지 않는다. 이 스킬의 결과는 후보이며, 최종 `decisionsForCEO` 포함 여부는 상위 에이전트가 다른 출처와 함께 판단한다.

## Output Structure

```json
{
  "project": "",
  "meetingTitle": "",
  "meetingAt": "",
  "meetingUrl": "",
  "meetingClaims": [],
  "confirmedDecisions": [],
  "unresolvedIssues": [],
  "ownerWork": [],
  "nextActions": [],
  "executiveDecisionCandidates": [],
  "internalConflicts": [],
  "limitations": []
}
```

배열 항목은 `Evidence Contract` 필드를 사용한다. 해당 내용이 없으면 빈 배열을 반환하며 사실을 만들지 않는다.

## Quality Check

- 회의록 밖의 사실을 추가하지 않았는가?
- 검토·제안을 확정 결정으로 올리지 않았는가?
- 담당자와 마감일을 추정하지 않았는가?
- 프로젝트 상태를 자체 판정하지 않았는가?
- 같은 사실을 결정·작업·다음 행동에 불필요하게 중복하지 않았는가?
- 다른 출처와의 충돌을 이 스킬이 임의 해결하지 않았는가?
- 근거 URL·시각·발췌가 가능한 범위에서 포함됐는가?
- 스펙 연결이 이름·작업항목·ID의 직접 근거 없이 추정되지 않았는가?
