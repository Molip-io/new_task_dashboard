## 프로젝트 현황 통합 브리핑 출력 보완

프로젝트 스펙과 동일하게, 프로젝트 현황도 허용된 여러 출처를 종합한 Agent 분석 결과로 작성한다. Slack 최신 발췌나 작업 건수 나열로 대체하지 않는다.

당일 `outputSchema`가 `projects[].projectBriefing`을 제공하면 새 분석에서 해당 객체를 작성한다. 과거 결과와 호환하기 위해 선택 필드여도 새 실행에서는 생략하지 않는다. 필드가 없는 이전 입력이면 기존 `projects[].summary`에 같은 분석 내용을 담고 새 필드를 임의 추가하지 않는다.

- `currentProgress`: `goal`, `milestones`, 활성 `specCatalog` 전체와 Notion·Slack·회의록·Git의 관련 직접 근거를 종합해 프로젝트의 목표, 주요 산출물, 현재 단계, 남은 범위를 설명한다. 일부 하위 작업의 완료를 상위 또는 프로젝트 전체 완료로 확대하지 않는다.
- `buildRelease`: 빌드·QA/리뷰·심사·배포/출시 현황을 버전·플랫폼별로 구분한다. 직접 근거가 없으면 `null`로 두고 확인 제한을 기록한다.
- `data`: 테스트·데이터 관찰 현황과 직접 확인된 결과를 해당 빌드·기간·국가·비교군과 함께 설명한다. 개발 중인 다음 버전, QA 후보, 이전 배포 버전의 결과를 같은 대상으로 합치지 않는다. 직접 근거가 없으면 `null`이다.
- `confirmationRequired`: 확인이 필요한 정보만 기록한다. 정보 부족을 실제 blocker로 승격하지 않는다.
- `nextActions`: 각 행동을 `{text, kind}`로 작성한다. `kind = agreed`는 직접 근거에서 합의된 행동이고 `suggested_check`는 AI가 제안하는 확인 행동이다.
- `evidence`: 위 프로젝트 결론에 직접 사용한 근거의 출처·시각·링크·발췌만 기록한다. 4종 출처를 맞추기 위해 없는 근거를 만들지 않는다.
- `confidenceLimits`: 출처 미수집, 원문 접근 제한, 버전 연결 불명확, 확인 시점 등을 기록한다.

실제 실행 병목은 기존 프로젝트 `blockers`에 기록하고, 기존 `summary`도 세 축을 압축한 대표 요약으로 유지한다. `project_operation`은 프로젝트 단위 근거이며 특정 스펙에 강제로 연결하지 않는다. 프로젝트 현재 진행은 `project_operation`만이 아니라 전체 스펙의 `recent_execution`과 필요한 `persistent_context`를 함께 종합한다.

저장 전에는 각 프로젝트의 `projectBriefing`이 실제로 작성됐는지, 원문 복사가 아닌 통합 설명인지, 다른 프로젝트·빌드가 섞이지 않았는지 검증한다. 기존 스프린트 범위·정량 규칙·쓰기 권한·최신성 검증·저장 후 검증은 그대로 유지한다.
